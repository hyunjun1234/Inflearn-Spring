엔터프라이즈급 DAG 기반 AI Workflow 설계

DAG 개념 요약

DAG(Directed Acyclic Graph, 방향 비순환 그래프)는 방향이 있는 간선으로 이어진 작업(정점)들 사이에 순환(돌아오는 길)이 없는 그래프를 뜻합니다. “선행 작업이 끝나야 다음 작업을 실행할 수 있다”는 의존 관계만 화살표로 이었을 때, 어떤 노드에서 출발해도 자기 자신으로 되돌아오는 경로가 없으면 그 구조가 DAG입니다.

그래프 이론·조합 최적화에서 방향 그래프의 한 종류로 오래 연구되어 왔고, 컴퓨터 과학에서는 위상 정렬·임계 경로·작업 스케줄링의 전형적인 모델입니다. 역사적으로 널리 쓰인 사례로는 컴파일 파이프라인(전처리→컴파일→링크 등 단계 의존성), Unix 계열 Make가 표현하는 파일 단위 빌드 의존 그래프, 패키지·모듈의 버전 의존성 그래프, 데이터 엔지니어링의 Airflow·Prefect 등에서의 ETL·배치 워크플로 DAG, 빅데이터 프레임워크의 실행 계획(연산 DAG), 일부 ML·실험 파이프라인에서의 단계 기록·재현 등을 들 수 있습니다.

본 과정에서는 멀티 에이전트 전략 분석 흐름을 같은 방식으로 설명하기 위해 DagWorkflowEngine이라는 이름과 WorkflowNode 단위 실행을 두었고, 그 개념을 Chapter 7에서 코드와 함께 처음 명시적으로 다룹니다.

한 줄로 정리

DAG는 “작업들 사이의 의존 관계와 병렬”을 한눈에 고정하는 표현이고, 본 장은 그걸 WorkflowNode와 DagWorkflowEngine으로 돌려 Ch8 선언적 워크플로로 이어가기 위한 디딤돌입니다.

Chapter 5에서는 Java 오케스트레이터와 ToolRegistry로 라우팅·병렬 분석·평가 등 단계·Tool 호출 순서를 코드에 고정하는 전략 분석 흐름을 봤습니다. 본 장은 그 같은 전략 분석 파이프라인을 ToolRegistry·전략 Tool 호출 체인 대신 DAG(Directed Acyclic Graph, 방향 비순환 그래프)—WorkflowNode와 간선—으로 풀고, 전용 엔진 DagWorkflowEngine이 그래프를 읽어 실행 가능한 노드를 스케줄링하는 형태로 바꾼 것을 다룹니다.

Chapter 5와 비교하면, 단계 제어는 여전히 “언제 무엇을 돌릴지”를 정하는 일이지만, Ch5는 Java 오케스트레이터가 ToolRegistry.require(…)로 Tool을 직접 호출하는 명령형 체인에 가깝습니다. 본 장은 그 제어를 DAG로 옮깁니다 — 작업은 WorkflowNode, “먼저 끝난 뒤에 다음”·병렬 분기는 방향 간선으로 적어 두고, 순환은 없게(acyclic) 두어 실행 순서가 그래프에서 바로 읽히게 합니다.

이중 구조 — 엔진(DagWorkflowEngine)은 이 그래프를 읽어 스케줄·동기화·의존성 해소까지 맡고, 노드 본문의 LLM 작업은 Chapter 4·5와 같이 SubAgentRegistry를 경유한 SubAgent로 멀티-LLM을 수행합니다.

엔진이 맡는 세 가지 (용어)

  • 스케줄 — 그래프에서 지금 돌려도 되는 노드를 골라 실행 큐에 넣는 일입니다. DagWorkflowEngine은 요청마다 라우터 → (SIMPLE이면 단순 응답만 / STRATEGIC이면 기술·시장 병렬 → 병합 → 평가·최적화 루프 등) 경로를 따라 다음 노드를 단계적으로 택합니다.
  • 동기화 — 여러 노드가 동시에 돌 때(예: 기술·시장 분석) 모두 끝난 뒤에만 병합·후속 단계로 넘어가게 맞춥니다. 본 저장소는 CompletableFuture로 병렬을 걸고 완료를 기다려 산출물을 한 시점에 모읍니다.
  • 의존성 해소 — “선행 노드가 끝나야 이 노드를 실행할 수 있다”는 조건이 만족될 때만 해당 노드를 실행 가능으로 둡니다. DAG는 순환이 없으므로 선행이 풀릴 때마다 다음 후보가 열리는 식으로 조건이 해소됩니다.

1. 개념 정리 (DAG 개념)

DAG(Directed Acyclic Graph, 방향 비순환 그래프)는 정점(노드)과 방향이 있는 간선(의존성)으로 이뤄진 그래프 구조인데, 어떤 노드에서 다시 자기 자신으로 돌아오는 순환 경로가 없다는 것이 핵심입니다.

  • Node(노드): 하나의 작업 단계 또는 처리 단위를 의미합니다. 이 예제에서는 라우팅, 단순 응답, 기술 분석, 시장 분석, 보고서 병합, 평가, 최적화 루프 등입니다.
  • Edge(간선): “어떤 노드가 끝나야 다음 노드를 실행할 수 있는지”를 나타내는 의존 관계입니다.
  • Acyclic(비순환): 노드들을 따라가다 보면 절대 다시 원래 노드로 되돌아오지 않습니다. 덕분에 실행 순서를 위에서 아래로(topological order) 명확히 정할 수 있고, 무한 루프에 빠지지 않도록 설계할 수 있습니다.

이 구조를 워크플로에 적용하면, “어떤 일을 어떤 순서·병렬·합성 규칙으로 실행할지”를 그래프 자체에 기록할 수 있습니다. 코드에서는 WorkflowNode 들이 DAG의 노드 역할을 하고, 각 노드는 inputs/outputs·의존성 정보로 서로 연결됩니다.

에이전트 관점에서의 DAG: DAG는 “하나의 거대한 에이전트”가 어떤 순서로 생각하고 도구를 쓸지를 암시해 두는 것이 아니라, 여러 작은 에이전트/노드가 어떤 순서와 병렬 패턴으로 실행될지를 그래프로 고정해 두는 방식입니다. 이 장의 DagWorkflowEngine은 이 그래프를 읽어 “지금 실행 가능한 노드”를 찾아 병렬/순차 실행하고, 모든 의존 노드가 끝났을 때 다음 노드를 스케줄링합니다.

4. Tool과 Node의 대응 (Chapter 5 vs 7)

Chapter 5의 Tool

  • 역할: 외부 연동·부작용은 @Tool·ToolRegistry로 실행 계층에 두고, Java 오케스트레이터가 어떤 Tool을 어떤 순서로 부를지 고정합니다.
  • 흐름: 사용자 질문 → 오케스트레이터가 단계별로 Tool·SubAgent 호출 → 컨텍스트에 쌓인 결과로 최종 답 생성.
  • 실습 맥락: StrategicAnalysisOrchestrator, @Tool, ToolRegistry 등으로 Java에서 오케스트레이션하는 예에 가깝습니다.
  • 특징: LLM이 임의로 Tool 순서를 짓기보다, 코드에 적힌 워크플로 안에서 Tool과 추론이 맞물립니다.

Chapter 7의 Node (WorkflowNode)

  • 역할: 전체 일을 DAG(방향 비순환 그래프)로 쪼인 워크플로의 한 단계입니다. 각 노드는 라우팅·단순 응답·병렬 분석·합치기·평가/최적화 루프 등 그래프 상의 위치가 정해져 있습니다.
  • 흐름: 질문 → DAG 엔진(DagWorkflowEngine)이 워크플로를 생성·실행(노드 스케줄·의존성 반영) → 결과.
  • 문서 표현대로 Agent가 실행이 아니라 워크플로 엔진이 실행에 가깝습니다.
  • 실습 맥락: DagWorkflowEngine, WorkflowNode, CompletableFuture로 의존성 조립·병렬 등 실행 제어가 Tool 중심 모델보다 명확합니다.

한 줄로 비교

구분 Ch5 Tool Ch7 Node
무엇의 단위인가 ToolRegistry에 등록된 실행 단위(도구) 그래프의 한 칸(단계·분기·병렬의 단위)
누가 흐름을 잡나 Java 오케스트레이터가 단계·Tool 호출 순서를 고정 DAG 엔진이 노드·의존성에 따라 실행
강점 실행 계층 분리, 서비스 연동에 적합 병렬·분기·루프 등 워크플로 제어·재현성

5. 언제 DAG가 필요한가

언제 DAG가 좋은지를 정리해 보면 다음과 같습니다.

  • DAG를 쓰는 게 좋은 상황
    • 단계가 많고, 선후관계·병렬·합류·단계별 오류 처리(예: 평가/최적화 반복)를 코드로 엄격하게 관리해야 할 때
    • “이 워크플로가 어제도, 다음 달에도 같은 순서와 병렬 패턴으로 돌아가야 한다”는 재현성/운영 요구가 있을 때
    • 여러 팀/서비스가 얽힌 대규모 분석 파이프라인, 리포트 생성 배치, 복수 데이터 소스 조합처럼 “한눈에 흐름을 보여줘야 하는 경우”
  • DAG가 과한 경우
    • 단계가 2~4개 정도로 단순하고, 병렬/분기가 거의 없을 때
    • “한 번 질문 → 한 번 답변” 또는 “에이전트 1~2개 정도가 Tool 몇 개 쓰는 수준”일 때
    • 아직 실험 단계라, 빠르게 형태를 바꾸면서 시도해 보고 싶은 POC(개념 증명)/프로토타입일 때

Spring AI 기준 단계별 추천

  • 1단계: 단일 Agent + Tool (Ch3~Ch5 스타일)
    대부분의 CRUD 백엔드 + 간단한 AI 기능, FAQ/요약/검색 정도는 여기서 충분합니다.
    Spring AI ChatClient + @Tool / 커스텀 Service 조합.
  • 2단계: Agent Runtime / TaskTool (Ch6 스타일)
    Think–Act–Observe 루프, Task 상태, 서브에이전트, 멀티 LLM 전략이 필요하면 이 층을 채택합니다.
    spring-ai-agent-utils + TaskTool + Markdown 서브에이전트.
  • 3단계: DAG-Orchestrated Workflow (Ch7 스타일)
    위 두 단계를 이미 쓰고 있고, “실행 순서를 그래프로 고정하고, 병렬/의존성/모니터링(필요 시 재시도 정책)을 강하게 설계해야 하는 수준”일 때 도입하는 단계입니다.
  • 4단계: 선언적 YAML + 검증 (Ch8·Ch9 스타일)
    같은 DAG 실행 아이디어를 YAML(DSL)로 정의하고(Chapter 8), 필요하면 Chapter 9처럼 로딩 파이프라인에 검증층을 두어 스케줄링 전에 선언 오류를 걸러 운영 안정성을 높입니다. 엔진·DSL 어휘는 YamlDagWorkflowEngine으로 Ch8·9에서 동일하게 쓰는 형태에 가깝습니다.

즉 AI + Workflow Engine 조합을 쓰되, 모든 요청을 DAG로 보내는 것이 아니라 라우팅·정책 계층이 난이도·요구사항에 따라 Agent+Tool / Agent Runtime / DAG 중 적절한 경로로 분기시키는 구조가 실무에서 가장 자연스럽습니다.

단일 서비스 기준으로 보면, 대부분은 1단계(Agent+Tool) 또는 2단계(Agent Runtime) 정도에서 머무는 경우가 많고, 정말 복잡한 코어 워크플로 일부에만 3단계(DAG)를 도입하는 식으로 “부분 적용”하는 패턴이 많습니다. 이 장의 핵심 메시지는 “장기적으로 보면, 실무에서 자주 보는 구조는 LLM(Agent) + Tool + Agent Runtime + (필요한 일부 흐름에 대해) DAG 같은 워크플로 엔진을 조합한 모습”에 가깝다는 것입니다. 즉, 회사 전체 관점의 아키텍처로 보면 네 단계 모두 등장할 수 있지만, 각 기능/마이크로서비스별로는 그 중 필요한 레벨까지만 선택해서 쓴다고 이해하시면 됩니다.
