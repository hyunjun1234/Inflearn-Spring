Chapter 6. Task-Orchestrated Multi-Agent

TaskTool 기반 Agent Runtime 설계

의존성: Maven org.springaicommunity:spring-ai-agent-utils (Artifact spring-ai-agent-utils, Spring AI Community 문서). 본 실습·문서는 버전 0.4.2 기준이며, 이하 agent-utils로 약칭합니다. 본 저장소에서는 Gradle 모듈 edu/build.gradle에 implementation 'org.springaicommunity:spring-ai-agent-utils:0.4.2' 를 선언해 이 의존성을 추가합니다.

Chapter 5에서는 Java 오케스트레이터와 ToolRegistry로 단계마다 어떤 Tool을 쓸지를 코드에 직접 정하는 방식을 봤습니다. 본 장은 그 대신 agent-utils의 Agent Runtime이 생각 → 행동 → 관측을 반복하는 쪽으로 넘어갑니다.

생각 → 행동 → 관측이 한데 묶인 루프입니다.

  • 생각 — 사용자 메시지·이전 결과를 보고, 모델이 다음에 무엇을 할지(어떤 Tool을 쓸지 등) 고름
  • 행동 — TaskTool · TodoWriteTool 등이 실제로 호출됨
  • 관측 — Tool이 돌려준 결과를 다시 모델에 넘겨, 다음 판단의 근거로 씀

Task마다 상태가 어떻게 바뀌는지까지 한 실행 엔진 안에서 처리합니다. 여러 Task와 서브에이전트를 Runtime이 조율하는 형태를 Task-Orchestrated Multi-Agent라고 부릅니다.

TaskTool은 Runtime에 붙는 Tool 하나로, .md에 적어 둔 서브에이전트 역할을 이름만으로 불러 씁니다. Runtime은 루프와 Task 진행을 돌리고, TaskTool은 Markdown 역할 정의와 Runtime을 잇는 연결 고리입니다.

StrategicTaskChatClientFactory로 ChatClient를 조립하고, StrategicAnalysisAgentConfig에서 빈 strategicAnalysisAgent를 만듭니다. 이 전용 ChatClient + agent-utils Tool 등록이 곧 이 실습에서 Agent Runtime을 붙이는 방식이며, 생각·행동·관측 반복과 Task·서브에이전트·할 일(Todo) 변화는 agent-utils 런타임이 맡습니다.

같은 Chapter 6 안에서도, 워크플로를 어디에 두느냐는 두 갈래로 나뉩니다. Java가 단계·분기·병렬·평가 루프까지 직접 밀어 나가는 쪽은 StrategicAnalysisTaskToolOrchestrator이고, system Markdown에 규칙을 모아 두고 생각 → 행동 → 관측 루프 안에서 Runtime이 다음 행동을 고르게 하는 쪽은 StrategicAnalysisTaskToolMDOrchestrator입니다. 실습·강의의 주 경로는 전자이며, 후자는 같은 TaskTool·서브에이전트 조립을 쓰되 흐름을 프롬프트에 더 맡긴 참고용 예제입니다. 자세한 대비는 아래 §5에서 정리합니다.

주 경로에서는 전략 분석을 몇 단계로 나누고 어떤 순서로 진행할지를 Java 오케스트레이터가 바깥에서 정합니다. 각 단계 안에서 문장을 만들고 서브 역할을 부르는 쪽은 strategicAnalysisAgent이고, TaskTool이 classpath:chapter6/agents/strategic/*.md에 정의된 서브에이전트를 호출합니다.

한 줄 요약 — 바깥(오케스트레이션)은 단계·순서(주로 Java, 선택적으로 system MD)를, 안쪽(Runtime + strategicAnalysisAgent)은 생각·행동·관측 루프와 Task 진행을 맡고, TaskTool이 .md 역할과 Runtime을 이어 줍니다.

2. 개념 정리 (agent-utils 구조)

이건 단순 Tool 사용이 아니라 Agent 실행 엔진(Runtime) 입니다. 개념도 위에서 설명했듯, TaskTool은 Runtime이 제공하는 실행 경로 위에 올라가는 구체적인 Tool이며, 본 실습에서는 그 TaskTool이 strategicAnalysisAgent ChatClient에 붙어 서브에이전트 호출을 담당합니다.

이 장에서 “Agent Runtime”은 코드 상 어디인가?

  • Agent Runtime에 해당하는 영역
    • StrategicAnalysisAgentConfig / StrategicAnalysisAgentMDConfig — strategicAnalysisAgent·strategicAnalysisAgentMd 빈을 선언하고, 시스템 프롬프트·workflowId 공급·Redis 단계 태그만 팩토리에 다르게 넘깁니다.
    • StrategicTaskChatClientFactory — STRATEGIC_SUBAGENTS·TaskTool·TodoWriteTool·ChatClient 조립을 단일 구현으로 제공합니다.
    • 이 ChatClient에 붙는 TaskTool (Markdown 서브에이전트 + DefaultTaskRepository)
    • TodoWriteTool — agent-utils Tool. 모델이 호출해 할 일 목록을 갱신하면, 팩토리 핸들러가 workflowIdSupplier·단계 태그(AGENT_TODO 등)로 WorkflowStatusPublisher → Redis/SSE에 스냅샷 전송
    • 이 조합이 사고–행동–관측 루프, Task 저장소, 서브에이전트 실행, Todo 관리 등 “Agent Runtime” 기능을 구현합니다.
  • 오케스트레이션(Java) 쪽 역할
    • StrategicAnalysisTaskToolOrchestrator / StrategicAnalysisAgentToolTaskService는 워크플로 조립자(Controller/Client)입니다.
    • StrategicAnalysisTaskToolMDOrchestrator는 같은 TaskTool·서브에이전트 조립을 쓰되, 단계·분기를 system Markdown에 더 맡기는 참고용 경로입니다. Java vs MD 대비는 §5입니다.
    • 언제 routing/technical-analysis/market-analysis/report-evaluator/report-optimizer를 호출할지,
    • 병렬/순차/루프 구조를 어떻게 가져갈지,
    • SSE 상태(예: 단계 이름, 평가 점수, Todo 스냅샷)를 어떻게 발행할지를 제어합니다.
  • 요약: Runtime = TaskTool + TodoWriteTool + TaskRepository + ChatClient 조립은 StrategicTaskChatClientFactory에 모이고, ch6의 오케스트레이터/서비스는 그 Runtime을 호출해 Chapter 6 전략 분석 시나리오를 만드는 층이라고 보면 됩니다.

3. 차이점 정리

  • Agent + Tool 패턴 (Ch5) = Tool 기반 애플리케이션 — LLM이 Tool을 선택하고 실행하는 구조
  • agent-utils 사용 (Ch6) = Agent Runtime 기반 시스템 — 본 장에서는 ChatClient(strategicAnalysisAgent)에 TaskTool을 올려 서브에이전트(.md)를 부르는 형태로 구체화됩니다.

Markdown(.md) 파일을 쓰느냐만이 핵심은 아니지만, 본 장 실습에서는 agent-utils의 TaskTool이 classpath:chapter6/agents/strategic/*.md 같은 서브에이전트 정의를 읽어, 역할·지시문을 자바 코드가 아닌 문서로 두고 이름 기반으로 호출할 수 있게 합니다. 즉 프롬프트·역할 분리를 재컴파일 없이 md로 조정하기 쉬운 쪽이 agent-utils 경로에 가깝습니다.

예시: Markdown 서브에이전트 정의

---
name: strategic-router
model: llama
description: >
  사용자의 요청을 SIMPLE / STRATEGIC 으로 분류합니다.
---

## 역할
- 입력 요청을 읽고, 복잡도와 요구 작업을 판단합니다.
- 단순 Q&A / 요약 수준이면 SIMPLE 로 분류합니다.
- 기술/시장 분석이 필요하면 STRATEGIC 으로 분류합니다.

## 출력 형식
- 반드시 "SIMPLE" 또는 "STRATEGIC" 만 대문자로 출력합니다.

같은 방식으로, RAG나 데이터베이스 연동을 위한 서브에이전트를 정의할 수도 있습니다. 

---
name: strategic-rag-search
model: gpt
description: >
  벡터 스토어에서 관련 문서를 검색하고, 검색 결과를 요약합니다.
---

## 역할
- 사용자의 질문을 기반으로 벡터 스토어를 조회합니다.
- 상위 N개의 관련 문서를 가져와 핵심 내용을 요약합니다.

## 출력 형식
- 검색된 근거 문서의 요약과, 질문에 대한 간단한 답변을 함께 제공합니다.
---
name: strategic-db-price
model: gpt
description: >
  PostgreSQL에서 여행 상품 가격 정보를 조회합니다.
---

## 역할
- 입력된 상품 ID 또는 여행 조건을 바탕으로 DB를 조회합니다.
- 관련된 가격 정보와 기간, 재고 상태를 정리합니다.

## 출력 형식
- 조회된 가격 목록과, 사용자가 이해하기 쉬운 가격 비교 요약을 제공합니다.

본 저장소에서는 전략용 .md 목록이 StrategicTaskChatClientFactory#STRATEGIC_SUBAGENTS에 한곳 정의되어 TaskTool에 연결됩니다. (예시로 아래처럼) 추가 서브에이전트를 TaskTool에 등록해 두면, 에이전트가 필요할 때 해당 서브에이전트를 호출해 문서/DB에서 실제 근거를 가져온 뒤, 그 결과를 다른 서브에이전트(분석·보고서 작성 등)와 결합해 보다 신뢰도 높은 답변을 만들 수 있습니다.

한편 Agent 실행 엔진(Runtime)은 ChatClient에 Tool을 몇 개 붙인 수준을 넘어, 사고 → 행동 → 관측 반복·Task 생명주기·서브에이전트 위임을 런타임이 구조적으로 담당한다는 뜻에 가깝습니다. 일반 Tool 방식에서도 모델이 여러 번 Tool을 부를 수는 있지만, 그 실행을 에이전트 전용 루프·Task 단위로 묶어 주는 층이 바로 이 Runtime입니다.

4. 가장 중요한 차이 (상세)

여러 개의 Tool을 쓰는 경우에도, 비교 축은 Tool 개수가 아니라 “다단계 실행을 어디에 두느냐”입니다. Ch5는 Agent + Tool 패턴, Ch6는 Agent Runtime(TaskTool)이 그 실행을 어떻게 묶느냐가 핵심입니다.

방식 실행 모델 (차이의 본질)
Agent + Tool 패턴 (Ch5) ChatClient + 여러 StrategicTool 또는 @Tool 을 등록해 두면, Java 오케스트레이터가 ToolRegistry.require(키).execute(...) 형태로 단계별로 적절한 Tool을 선택·실행합니다. LLM은 주로 “질문 이해 + 결과 해석”에 집중하고, 다단계 실행 흐름은 오케스트레이터 코드에 녹아 있습니다. Agent Runtime·Task 생명주기·명시적 사고–행동–관측 루프는 별도로 제공되지 않습니다.
agent-utils 방식 (Ch6) Agent Runtime이 사고 → 행동 → 관측 같은 반복 실행과 Task·상태·서브에이전트 위임을 전제로 다단계 실행을 구조적으로 다룹니다. 이 장에서는 TaskTool이 StrategicTaskChatClientFactory를 통해 ChatClient에 등록되어 Markdown 서브에이전트(classpath:chapter6/agents/strategic/*.md)를 이름으로 호출하는 실행 입구 역할을 하고, TodoWriteTool과 TaskRepository가 Task 상태와 진행 상황을 관리합니다. Tool이 여러 개인 점은 Ch5와 같을 수 있지만, 다단계 실행 루프와 Task 관리가 “Agent Runtime” 레벨로 올라간다는 것이 가장 큰 차이입니다.

5. Java 오케스트레이터와 MD(system) 오케스트레이터 — StrategicAnalysisTaskToolOrchestrator vs StrategicAnalysisTaskToolMDOrchestrator

앞 절들은 Chapter 5 vs Chapter 6(실행 모델이 Agent+Tool인지, Agent Runtime+TaskTool인지)를 기준으로 했습니다. 이 절만큼은 축을 바꿔, 같은 Ch6 구성요소를 쓰면서도 “워크플로를 코드에 쓸지, system 프롬프트에 쓸지”를 나눕니다.

비교의 핵심은 한 가지입니다. Java가 라우팅·병렬·평가 루프 같은 단계 제어를 직접 수행하는지, 아니면 system Markdown(예: prompts/strategic-analysis-agent-system.md)에 routing·분석·평가·개선·TodoWrite 규칙을 모아 두고 생각 → 행동 → 관측 루프 속에서 Runtime이 다음 Tool 호출을 고르게 할지입니다. 아래 두 클래스가 각각 이 두 방식에 대응합니다.

StrategicAnalysisTaskToolOrchestrator — 전형적인 Java 오케스트레이터입니다. 라우팅, 간단 응답, 기술·시장 병렬 분석, 평가, 개선까지 어느 단계를 언제 돌릴지가 메서드·분기·스레드 풀·루프로 소스에 드러납니다. 각 단계 안에서만 strategicAnalysisAgent와 TaskTool로 Markdown 서브에이전트를 부릅니다. Redis 발행, 예외 처리, 재시도 정책도 타입이 있는 코드를 따라가면 되므로 운영·디버깅·회귀 테스트에 유리합니다.

StrategicAnalysisTaskToolMDOrchestrator — 흐름을 MD(system)에 더 맡기는 최소 예제입니다. @Qualifier("strategicAnalysisAgentMd") ChatClient는 StrategicAnalysisAgentMDConfig가 StrategicTaskChatClientFactory로 만든 빈입니다. TaskTool과 서브에이전트 목록은 주 경로와 동일하고, 달라지는 것은 system 프롬프트와 Todo용 Redis 태그 정도입니다. 사용자 입력을 한 번 넘기면, 위 규칙들을 system Markdown에 묶어 둔 채 Runtime이 순서를 풀어 갑니다. Java 쪽은 executeWithMonitoring에서 호출을 걸고 시작·완료·오류 같은 상태만 남기는 얇은 층에 가깝습니다. 소스 주석대로 참고용이며, HTTP·컨트롤러 연동은 수업 범위 밖에서 선택할 수 있게 둔 형태입니다.

Spring AI·Spring Boot 기반 엔터프라이즈 백엔드에서는 요청 단위 제어 흐름(control flow)과 순서, 병렬 실행(동시성) 경계, 예외·재시도·실패 처리 경계, Redis·SSE를 통한 진행 상태·이벤트 발행(observability)까지 정적 타입·테스트 스위트로 명세하고 회귀 검증하기 쉬울수록 운영 가시성과 교육 목표(재현 가능한 실행 모델 습득)에 직결되기 때문입니다.

반면 오른쪽 열처럼 라우팅·분석·평가·TodoWrite까지 system Markdown·프롬프트에 맡기고 Java는 얇은 진입점만 두면, 앞 문단에서 말한 제어 흐름·동시성·실패 경계·상태 발행이 LLM 추론·Tool 호출 로그에 흩어져 보이기 쉽습니다. 빠른 스파이크·프롬프트 실험에는 부담이 적지만, 팀 단위로 서비스화할 때는 컴파일·리뷰·테스트로 워크플로를 고정하기 어렵고, 표에서 오른쪽 열이 약한 것처럼 단계별 SLA(서비스 수준 협약: 지연·가용성 등 단계마다 지켜야 할 목표)·보상 트랜잭션·감사 추적처럼 경계가 명시적이어야 하는 요구를 맞추기도 훨씬 까다롭습니다.

그래서 본 과정에서는 주 경로를 StrategicAnalysisTaskToolOrchestrator로 두고, StrategicAnalysisTaskToolMDOrchestrator는 같은 Runtime 위에서 “프롬프트 쪽에 흐름을 더 맡기는 설계”를 보여 주는 참고용 예제로만 둡니다. 두 구현을 나란히 읽어 보면, 수업에서 Java 오케스트레이션을 먼저 익히는 이유가 한 번에 정리됩니다.

7. 핵심 결론

이 장 전체를 한 번에 짚는 요약입니다. 앞의 Ch5 대비·오케스트레이션 논의와 이어집니다.

  • Agent + Tool (Chapter 5) — LLM에 도구를 붙여 기능을 확장하는 패턴입니다. Tool을 여러 개 두거나 여러 번 호출할 수 있지만, 그것만으로 Ch6와 구분되지는 않습니다.
  • agent-utils (Chapter 6) — 그 위에 Agent Runtime·Task를 얹어, 생각 → 행동 → 관측과 Task 진행을 런타임이 구조적으로 맡기 쉬운 층입니다.
  • 본 장 실습에서의 TaskTool — ChatClient(예: strategicAnalysisAgent)에 붙는 Tool 가운데 하나로, Markdown 서브에이전트를 부르는 실행 입구(관문)입니다. 이 조립은 본 저장소에서 StrategicTaskChatClientFactory에 한곳에 모아 둡니다.

비교할 때 둘을 “Tool 한 개 vs 여러 개”로만 나누면 오해가 생깁니다. 실행을 어떤 층에서 묶느냐—한 번의 대화, Java 오케스트레이터 코드, Agent Runtime, Task 단위 등—를 기준으로 보는 편이 안전합니다. TaskTool은 그중 “ChatClient에 등록된 Tool”로서 서브에이전트 호출로 이어지는 구체적인 입구입니다.
