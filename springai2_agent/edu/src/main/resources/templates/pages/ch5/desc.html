Chapter 5 실습 가이드 — Tool-Orchestrated Multi-Agent (Tool로 실행 층 분리)

Chapter 4에서는 역할 키로 서브에이전트를 직접 조회해서 진행 했습니다.
Chapter 5는 그 위에 도구 전용 추상화를 둡니다. 같은 전략 분석 흐름(라우팅, 단순/전략 분기, 병렬 분석, 평가·개선)을 이름으로 등록된 “도구”를 통해 호출하고, 각 도구 안은 다시 이전 장과 같이 서브에이전트 레지스트리에 위임하는 이중 층입니다. 관측은 여전히 HTTP 경계와 Redis·SSE 단계 이벤트로 묶습니다. 다만 할 일 스냅샷을 Redis로 보내는 Todo 이벤트는 이 장 경로에는 두지 않습니다. 이후 장에서는 도구 대신 Task·Markdown·에이전트 런타임으로 옮기고, 더 나아가 그래프 엔진으로 분기·병렬을 표현합니다.

3. 도구 빈 · SubAgent 키 · 모델

각 StrategicTool은 Tool#name()과 같은 문자열을 SubAgentRegistry#require(…)에 넘겨, 동일 키로 등록된 SubAgent 빈에 LLM 호출을 위임합니다(패키지 com.ai.app.agent.subagent).

호출 형태는 도구마다 조금씩 다릅니다. 예: ReportOptimizerTool은 초안·평가문을 합쳐 ReportOptimizerSubagent.combinedUserMessageForRegistry(…) 규칙으로 한 문자열을 만든 뒤 execute합니다.

4. API·DB·RAG 기반 컨텍스트 주입(Context injection)과 SubAgent 호출

Tool 레이어를 두는 이유 중 하나는, LLM만으로는 갖기 어려운 외부 근거·실시간 상태를 끌어와 서브에이전트 호출의 입력(프롬프트 본문)에 섞을 수 있기 때문입니다. REST API, 데이터베이스, 벡터 스토어(RAG) 등으로 수집한 문자열을 한 덩어리로 묶은 뒤 SubAgent#execute(user, system)에 넘기면, 동일한 레지스트리 키(market-analysis 등)를 유지한 채 근거 있는 분석으로 확장할 수 있습니다.

MarketAnalysisTool.java 클래스 주석에는 이런 확장을 가정한 설명이 들어 있습니다. 외부 API / Database / Vector Store(RAG)에서 모은 시장 데이터·리포트를 프롬프트에 포함하는 예시가 주석으로만 붙어 있으며, Chapter 5에서 “Tool + RAG/DB 연동” 패턴을 설명할 때 참고용으로 쓸 수 있다고 적혀 있습니다.

예시 1 — API / Database → 통합 프롬프트 → SubAgent

파일 하단 블록 주석의 예시 1은 가상의 MarketPriceClient, TrendRepository로 가격·프로모션 정보와 내부 실적·트렌드를 조회한 다음, [사용자 요청]·[외부 가격/프로모션 데이터]·[내부 트렌드/실적 데이터] 섹션으로 나눈 단일 user 메시지를 만든 뒤 subAgentRegistry.require(name()).execute(prompt, systemMessage())로 넘기는 흐름입니다. 즉 데이터 수집은 Tool(또는 Tool이 호출하는 서비스), 문장 생성은 SubAgent에 두는 분리입니다.

예시 2 — Vector Store(RAG) → 컨텍스트 주입 → SubAgent

예시 2는 RagSearchService로 벡터 검색 결과를 context 문자열로 만든 뒤, 사용자 질문과 함께 프롬프트를 구성하고, 필요 시 strategic-rag-search 같은 별도 서브에이전트 키를 subAgentRegistry.require("strategic-rag-search")로 호출하는 패턴을 보여 줍니다.

현재 실습에 포함된 execute(String input) 구현은 사용자 입력만 넘기는 최소 경로이고, 위 주석은 향후 API·DB·RAG 와 같은 다양한 외부 데이터 연동 시 사용이 가능 합니다.
오케스트레이터가 단계만 고정하고, “무엇을 프롬프트에 넣을지”를 Tool 안에서 다양한게 추가 할 수 있습니다.
