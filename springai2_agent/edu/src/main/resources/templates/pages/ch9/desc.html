Chapter 9. Validated Agent Workflow DSL — 실습 가이드

Chapter 8에서는 YAML(DSL)로 워크플로를 선언하고 YamlDagWorkflowEngine이 읽어 실행했습니다.
Chapter 9 실습에서는 엔진과 DSL 어휘는 그대로 두고, chapter9/dagworkflow/*.yml을 로드한 뒤 WorkflowDefinitionValidator를 통과한 정의만 캐시해 엔진에 넘깁니다.

이제는 엔진(YamlDagWorkflowEngine 예시)이 “어느 노드를 언제 실행할지”를 YAML에 기록된 노드/간선/조건/루프 설정을 기준으로 판단하고, 각 노드는 실행 컨텍스트에 사용자 입력·라우팅 결과·병렬 분석 결과·평가/최적화 결과를 누적합니다. 노드 내부에서는 필요할 때 SubAgent(역할별 LLM)나 보고서 최적화 단계를 호출합니다.

이 실습의 초점은 로딩 파이프라인의 검증층입니다. 워크플로 확장은 여전히 YAML만 추가·수정하면 되고, 오타·잘못된 dependsOn·사이클·필수 필드 누락 같은 선언 오류는 스케줄링 전에 걸러 냅니다(실행 엔진·노드 매핑은 Chapter 8과 동일).

Spring에서는 ObjectMapper(YAML)나 snakeyaml를 활용하거나, @ConfigurationProperties로 바인딩해 WorkflowDefinition 집합을 만들어 둘 수 있습니다. 이 정의를 기반으로 엔진은 동적으로 노드 그래프를 구성합니다.

3. 실행 엔진과 노드 매핑

엔진은 정의를 바탕으로 다음과 같은 정보를 조합해야 합니다.

  • 어떤 순서로 실행할 수 있는지 (의존성이 없는 노드 → 병렬 실행 가능)
  • 어떤 조건에서 실행할지 (when 식 평가, 예: route.category == 'STRATEGIC')
  • 어떤 Node 핸들러에 연결할지 (handler 값을 Bean/Registry에 매핑)

실습에서는 실제 구현 대신, Ch7의 DagWorkflowEngine 구조를 떠올리면서 “이 로직을 YAML 정의에 기반한 일반화된 엔진으로 빼면 어떻게 될까?”를 중심으로 코드를 읽어보면 좋습니다.

4. 운영·버전 관리 관점

YAML 기반 워크플로는 코드와 분리된 버전 관리가 가능합니다. 예를 들어, strategic-analysis-v1.yml, strategic-analysis-v2.yml를 나란히 두고 workflowId나 헤더 값에 따라 다른 정의를 선택할 수 있습니다.

또한, YAML에만 변경이 있을 경우에는 애플리케이션 코드 배포 없이도 워크플로를 교체할 수 있고, 문제가 생기면 이전 YAML로 되돌리는 롤백이 쉬워집니다.
