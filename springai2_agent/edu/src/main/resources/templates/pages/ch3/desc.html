Strategic Analysis 흐름


적용 패턴 (코드 대응)
1) Routing Workflow → LLaMA가 SIMPLE / STRATEGIC 이진 분류; SIMPLE이면 여기서 종료
2) Parallelization Workflow (STRATEGIC만) → GPT(기술적 관점 분석) + Gemini(시장 트렌드 분석)를 CompletableFuture·고정 풀(4)로 병렬, thenCombine으로 병합
3) Evaluator-Optimizer (STRATEGIC만) → Gemini 검토(PASS/개선) 후 미통과 시 GPT 수정, 최대 4회
4) 단계 전환·상태는 publishStatus(Redis)로 발행 — 별도 Orchestrator Bean 없이 본 서비스 메서드가 순서 제어

모델 사용 이유
- GPT: STRATEGIC 시 기술 병렬 분석 및 Optimizer(피드백 반영 수정)
- Gemini: STRATEGIC 시 시장 병렬 분석 및 Evaluator(검토·PASS)
- LLaMA: SIMPLE/STRATEGIC 라우팅 및 SIMPLE 경로 단답

특징
- STRATEGIC일 때만 CompletableFuture 병렬 및 평가 루프
- Redis 기반 실시간 상태 모니터링
- Worker 내부 예외 시 플레이스홀더 문자열 처리
- 반복적 품질 개선 루프(최대 4회)

Precision Execution 흐름


적용 패턴 (코드 대응)
1) Refining (LLaMA) — publishStatus(Refining); SRS 변환 시스템 프롬프트 + rawIdea → refinedIdea
2) Orchestrator (GPT) — Worker_A/B 할당량을 텍스트로 생성, 출력 tasks를 이후 두 Worker 입력으로 공유 (의존성 그래프·스케줄러 없음)
3) Workers — GPT(코드를 작성하세요.)·Gemini(가이드 문서를 한글로 작성하세요.)가 동일 tasks로 CompletableFuture 병렬, 풀 크기 4
4) Aggregation — join() 후 --- 개발 코드 --- / --- 사용 설명서 --- 포맷으로 결합 (별도 정합성·누락 검증 단계 없음)

모델 사용 이유
- GPT: Orchestrator(작업 지시 문자열) + Code Worker
- LLaMA: SRS Refiner
- Gemini: 한글 가이드 Doc Worker

특징
- Redis 상태: Refining, Orchestrator, Workers, Aggregation, COMPLETED (오류 시 Error)
- 단계별 예외는 safeCall로 흡수해 오류 메시지 문자열을 산출에 반영
- Workers 병렬은 CompletableFuture + 전용 고정 스레드 풀(크기 4)
- Refining부터 Aggregation까지 단계 경계마다 로깅

Voting Analysis 흐름


적용 패턴 (코드 대응)
1) 병렬 호출 — CompletableFuture.supplyAsync(..., newFixedThreadPool(4)), 각 Future는 exceptionally로 실패 시 오류 문자열 반환
2) 수집 — join()으로 리스트화; 별도 유효성 검증·재시도 없음
3) Judge — GPT에 3개 답을 라벨과 함께 전달, 시스템 문구로 선택·결과·사유 요청
4) 반환 — 세 모델 원문 + ===== 최종 판정 ===== 블록을 한 문자열로 결합

모델 사용 이유
- GPT: 1차 답변(객관적 지표) + 최종 판정관
- Gemini: 데이터·통계 성향 답변
- LLaMA: 실행 가능성 성향 답변

특징
- Redis 상태: VOTING_START, AGGREGATING, COMPLETED
- CompletableFuture + 고정 스레드 풀
- Judge 실패 시 오류 문자열을 최종 판정으로 사용
- 가중치 투표·Judge 교체·Self-Eval 등은 본 코드에 없음
4. Auto Pattern Routing 질문 유형에 따라 Strategic / Precision / Voting 중 하나를 자동 선택하는 오케스트레이션 진입점

실행 흐름 (AutoPatternRoutingService#executeWithMonitoring)
입력 수신 → LLaMA로 패턴 분류 → 선택된 서비스의 executeWithMonitoring 위임 → 해당 파이프라인의 단계·응답·상태 발행까지 동일 흐름으로 이어집니다.

모델 사용 이유

- 실행 단계의 GPT·Gemini·LLaMA 조합은 선택된 서비스(위 1~3행)와 동일

특징
- Redis/SSE 상태 예시: STARTED → PATTERN_ROUTING → PATTERN_SELECTED → (선택된 서비스의 단계들) → COMPLETED
- NDJSON·Redis/SSE 관측 모델은 세 완성형 서비스와 동일
- REST: POST /ch3/auto-pattern-routing · prompt, workflowId
