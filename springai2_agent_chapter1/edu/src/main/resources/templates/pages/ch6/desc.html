실습 STEP A
요청과 응답

POST /ch6/strategic-analysis로 prompt, workflowId(UUID)를 보냅니다. HTTP 응답 본문은 최종 결과 문자열입니다.

실습 STEP B
SSE 연결

EventSource로 /api/workflow/stream/{workflowId}를 구독합니다. 실습 스크립트는 일정 시간 후 연결 종료를 시도할 수 있습니다. 단계 이벤트는 StrategicAnalysisAgentToolTaskService(시작·에이전트 단계 등)와, 에이전트가 호출하는 TodoWriteTool(할 일 목록이 바뀔 때마다 AGENT_TODO 단계로 스냅샷 문자열을 넣는 쪽)이 WorkflowStatusPublisher로 Redis/SSE에 발행합니다.

실습 STEP C
오케스트레이터와 에이전트 구성

순서·분기는 자바 StrategicAnalysisTaskToolOrchestrator가 잡습니다. 예를 들어 언제 라우팅할지, 기술·시장 분석을 동시에 돌릴지, 평가·개선을 몇 번 돌릴지 같은 워크플로 골격입니다. 그 안에서 쓸 ChatClient는 StrategicTaskChatClientFactory가 만듭니다. 서브에이전트 목록(STRATEGIC_SUBAGENTS), TaskTool, TodoWriteTool, 여러 LLM 빌더, ToolCallAdvisor를 한 번에 조립합니다. TodoWriteTool은 agent-utils가 붙이는 Tool로, 모델이 호출해 할 일 목록을 바꿀 때마다 팩토리의 todoEventHandler가 항목을 한글 요약 줄로 펼쳐 WorkflowStatusPublisher#publishStatus에 넘깁니다. StrategicAnalysisAgentConfig는 그 팩토리에 시스템 지시문(Java 상수 STRATEGIC_TASK_SYSTEM_INSTRUCTION)·현재 요청의 workflowId(StrategicWorkflowContext)·Redis에 쓸 Todo 태그(AGENT_TODO)만 넘겨 strategicAnalysisAgent 빈을 등록합니다.

정리하면, 오케스트레이터는 “지금은 어떤 단계인가”만 밀어 주고, routing 같은 이름으로 Markdown 서브에이전트를 실제로 호출하거나 할 일을 Redis로 보내는 일은 Agent Runtime이 붙은 ChatClient 쪽에서 이뤄집니다. Runtime에 무엇을 태울지는 StrategicTaskChatClientFactory#buildStrategicTaskChatClient 한곳에 모아 두었고, classpath:/agents/strategic/strategic-*.md 파일들은 목록 STRATEGIC_SUBAGENTS로 TaskTool에 연결되어 이름으로 불립니다.

strategicAnalysisAgentMd는 StrategicAnalysisAgentMDConfig가 같은 팩토리를 쓰되, system 지시를 Markdown 파일로 두고 Todo 단계 태그만 AGENT_TODO_MD로 바꾼 빈입니다. StrategicAnalysisTaskToolMDOrchestrator는 Java로는 진입·SSE만 얇게 두고, 라우팅·분석·평가 등 워크플로 문장을 자바 메서드 체인이 아니라 prompts/strategic-analysis-agent-system.md(system Markdown)과 classpath:/agents/strategic/*.md 서브 정의에 더 실어 둔 참고용 예시입니다 — 본문 §5 Java vs MD와 같은 축입니다. 본 과정의 주 경로는 StrategicAnalysisTaskToolOrchestrator(코드로 단계·순서를 잡는 쪽)이며, MD(system) 조합은 같은 Runtime에서 “흐름을 프롬프트·.md로 조정할 수 있다”는 대비를 보여 주는 참고용으로만 둡니다.

Chapter 6은 팩토리 + 설정 클래스로 Task 기반 ChatClient를 만들어 오케스트레이터가 주입받아 쓰는 구조입니다.

포인트: Chapter 4·5 쪽은 ToolRegistry나 SubAgentRegistry에서 자바 도구 빈을 키로 꺼내 바로 실행하는 그림에 가깝습니다. Chapter 6에서는 StrategicAnalysisTaskToolOrchestrator가 그렇게 직접 부르기보다, runSubAgent("routing", …)처럼 strategicAnalysisAgent ChatClient에게 “task 도구로 routing 같은 이름의 서브를 불러라”는 사용자 메시지를 넘깁니다. 그러면 Runtime이 TaskTool을 통해 Markdown에 정의된 서브에이전트를 고르고, 실제 문장·분석 생성은 그 .md 프롬프트를 탄 ChatClient 쪽에서 이뤄집니다. 예전 경로(StrategicTool 등)와 “레지스트리 직결” vs “ChatClient + TaskTool + Markdown”으로 나뉜다고 기억하면 됩니다.

StrategicWorkflowContext를 두는 이유: Agent Runtime과 Tool 호출이 안쪽으로 여러 번 이어질 때, 매 단계마다 workflowId를 인자로 넘기면 시그니처가 지저분해지고 빠뜨리기 쉽습니다. 그래서 HTTP 요청을 처리하는 스레드마다 “지금 이 요청의 워크플로 id”를 ThreadLocal에 한 번 심어 두고, TodoWriteTool 핸들러는 workflowIdSupplier(StrategicWorkflowContext::getWorkflowId)로 그 id를 꺼내 publishStatus(workflowId, todoPublishStage, 메시지) 형태로 보냅니다(기본 빈은 todoPublishStage가 AGENT_TODO). 클라이언트는 같은 workflowId의 SSE에서 할 일 스냅샷을 실시간으로 받습니다.

이 ThreadLocal은 Chapter 4·5 HTTP 실습 경로에서는 쓰지 않고, Chapter 6에서만 위 목적으로 com.ai.chapter6.service.StrategicAnalysisAgentToolTaskService 진입에서 set하고 처리가 끝나면 clear합니다.

3. 엔드투엔드 흐름

생각 → 행동 → 관측

  1. 생각 — LLM이 “다음에 어떤 Tool을 쓸지” 정함
  2. 행동 — Runtime이 TaskTool·TodoWrite를 실제 호출
  3. 관측 — Tool 결과가 모델로 돌아감 · SSE는 화면용

생각

strategicAnalysisAgent에 연결된 LLM이 “지금까지의 대화·Tool 결과를 보고 다음에 무엇을 할지” 고릅니다(보통 어떤 Tool을 호출할지). 전체 순서(언제 routing·병렬 분석을 할지)는 자바 StrategicAnalysisTaskToolOrchestrator가 정하고, 각 단계 안에서는 runSubAgent(…)로 넘기는 사용자 한 줄이 LLM의 입력이 됩니다.

행동

Agent Runtime이 모델이 고른 대로 Tool을 실제로 실행합니다. TaskTool은 classpath:/agents/strategic/*.md 서브에이전트를 돌리고, TodoWriteTool은 할 일 목록을 바꿉니다. 할 일이 바뀌면 팩토리(StrategicTaskChatClientFactory)가 Redis/SSE로도 넘기도록 묶어 두었습니다. 이 모든 조립은 strategicAnalysisAgent 빈 하나에 들어 있습니다.

관측

Tool이 돌려준 내용이 다시 모델에게 전달되어 다음 판단에 쓰입니다. 한편 진행률·체크리스트는 WorkflowStatusPublisher → SSE로 같은 workflowId에 올라갑니다(Orchestrator의 스냅샷 + TodoWriteTool). 이건 브라우저가 보는 진행 표시용이고, 모델이 다음 턴에 참고하는 “관측”과는 목적이 다릅니다.

4. SSE 단계와 TodoWrite

대표 Redis/SSE step 흐름:

  • STARTED, AGENT, AGENT_TODO(Todo 스냅샷), COMPLETED 또는 ERROR

Chapter 5 경로와 비교하면 AGENT_TODO가 Chapter 6에서 두드러집니다. TodoWriteTool은 agent-utils가 ChatClient에 붙이는 일반 Tool이라, Runtime이 루프를 돌며 모델이 스스로 “할 일 쓰기/갱신”을 호출할 수 있습니다. 본 저장소 팩토리(StrategicTaskChatClientFactory)에서는 그때마다 todoEventHandler가 목록을 짧은 한글 문장으로 펼쳐, StrategicWorkflowContext에서 꺼낸 workflowId와 설정에서 넘긴 단계 태그(예: AGENT_TODO, MD 예제는 AGENT_TODO_MD)로 WorkflowStatusPublisher에 넣습니다. 브라우저는 /api/workflow/stream/{workflowId} 구독으로 그 메시지를 Todo 진행률·체크리스트 스냅샷처럼 받게 됩니다.

같은 단계를 Chapter 5에서는 ToolRegistry에 등록한 StrategicTool 빈이 맡고, Chapter 6에서는 classpath:/agents/strategic/*.md 서브에이전트(frontmatter name = TaskTool 키)가 맡습니다. 아래는 파일·역할 요약과, Chapter 5에서 대응하는 Tool 클래스입니다.

모델 지정 방식

각 .md 파일 상단 YAML(frontmatter)의 model:에 별칭을 적습니다. TaskTool이 해당 서브에이전트를 실행할 때 ClaudeSubagentExecutor가 StrategicTaskChatClientFactory#strategicModelBuilders로 별칭을 받아, 실제로는 아래처럼 Spring에 주입된 채팅 모델 빈에 연결된 ChatClient.Builder를 고릅니다.

별칭 (model:) 연결되는 빈 (본 저장소 기준)
default OpenAiChatModel (GPT 계열)
cheap OllamaChatModel (가벼운 로컬/저비용)
heavy GoogleGenAiChatModel (Gemini)
gpt · llama · gemini 각각 OpenAI / Ollama / Gemini — 위와 동일 매핑으로 직접 지정할 때 사용

이번 장 예제 파일에서의 사용: strategic-router.md는 model: default, strategic-simple.md는 model: cheap, 나머지(strategic-tech, strategic-market, strategic-evaluator, strategic-optimizer)는 모두 model: heavy입니다. 즉 라우팅은 기본 GPT, 단순 응답은 Ollama, 분석·평가·개선처럼 부담이 큰 단계는 Gemini를 쓰도록 나뉘어 있습니다. 별칭만 바꾸면 같은 Markdown으로 다른 모델을 태울 수 있습니다.
