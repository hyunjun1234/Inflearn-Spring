Chapter 4 실습 가이드 — Multi-Agent (SubAgent·레지스트리)

이전 장까지는 주로 한 오케스트레이션 코드 안에서 모델을 직접 호출하는 패턴을 공부 했습니다.
Chapter 4에서는 같은 비즈니스 흐름(라우팅 → 단순 응답 또는 전략 분석, 전략이면 기술·시장 병렬 분석 → 초안 평가·개선 루프)을 역할마다 나뉜 서브에이전트로 실행합니다. 각 단계는 고정된 이름(키)으로 레지스트리에서 꺼내 호출하고, 시스템 프롬프트는 구현체마다 갖습니다. 도구 전용 레이어(Spring AI @Tool에 대응하는 별도 추상화)는 두지 않고, 서버 안에서 이름 조회와 LLM 호출만으로 단계를 밟습니다. 관측은 HTTP 요청·응답 경계와, Redis에 단계 이벤트를 쌓고 SSE로 구독자에게 흘리는 구조로 묶입니다. 이후 장에서는 같은 단계 의미를 도구 레지스트리·전략 도구 인터페이스로 감싼 뒤, 더 나아가 Task/Markdown·DAG 등으로 확장합니다.

실습 로그에 자주 보이는 단계 이름

  • ROUTING — routing SubAgent가 여기서 SIMPLE인지 STRATEGIC인지 갈라 줍니다.
  • SIMPLE — simple-query만 타고, 긴 파이프라인 없이 마무리되는 경로입니다.
  • ANALYZING — STRATEGIC이면 technical-analysis와 market-analysis를 병렬로 돌린 다음, 결과를 한 덩어리로 합칩니다.
  • EVALUATING / OPTIMIZING — report-evaluator로 품질을 보고, 필요하면 Optimizer가 초안을 고치는 것을 반복합니다(최대 4회).

이 이벤트들은 WorkflowStatusPublisher가 Redis로 보내 주는 것이며, 브라우저는 같은 workflowId로 SSE를 열어서 받아 보는 구조입니다.

4. STRATEGIC 경로 — 병렬·평가·개선 루프

실습에서 로그가 길게 이어지는 것은 보통 이 STRATEGIC 경로 때문입니다. 아래 순서만 따라가 보시면 Chapter 본문에 있는 요약과 딱 맞아떨어집니다.

  1. ROUTING — 먼저 라우팅 SubAgent가 돕니다.
  2. STRATEGIC으로 갈렸을 때 — 기술(GPT) + 시장(Gemini)을 CompletableFuture로 병렬 돌리고, 나온 문자열 두 개를 하나의 초안으로 합칩니다.
  3. EVALUATING / OPTIMIZING — 평가 SubAgent가 통과인지 봅니다(PASS 같은 표시). 안 되면 Optimizer가 초안을 고치고, 다시 평가로 돌아갑니다.

그래서 화면에서는 대략 Routing → (병렬) Analysis → Merge → Evaluate ⇄ Optimize 같은 리듬이 SSE에 그대로 보이게 됩니다. Chapter 3의 StrategicAnalysisService와 비즈니스로는 같은 이야기이며, Chapter 4에서는 그것을 SubAgentRegistry 역할 키 단위로 쪼개 올린 것이라고 이해하시면 다음 장으로 넘어가기 편합니다.

5. 레지스트리 키·모델

코드는 StrategicAgentKeys 상수와 com/ai/shared/agent/subagent 구현을 맞춰 둔 요약표입니다. 실습 중에 “지금 로그에 나온 단계가 어떤 키와 연결되는가?” 하실 때 펼쳐 보시면 됩니다.

레지스트리 키 (name()) 실습에서 하는 일 모델 (대표)
routing 요청을 SIMPLE / STRATEGIC으로 분류 Llama
simple-query SIMPLE 경로에서 짧은 답만 생성 Llama
technical-analysis STRATEGIC 경로 — 기술 관점 분석(병렬 워커) GPT
market-analysis STRATEGIC 경로 — 시장·트렌드 분석(병렬 워커) Gemini
report-evaluator 병합 초안 품질 평가, 통과 시 응답에 PASS 포함 Gemini
report-optimizer 평가 미통과 시 초안에 평가 피드백을 반영해 개선(EVALUATING/OPTIMIZING 루프) GPT

6. 다른 Chapter와 이어지는 맥락

마지막으로, 지금 배운 내용이 앞뒤 장에서 어떻게 확장되는지만 짚고 마무리합니다.

  • Chapter 3 — 한 서비스 클래스 안에서 ChatClient를 여러 번 직접 부르는 오케스트레이션.
  • Chapter 4 (지금 실습) — StrategicAnalysisAgentOrchestrator가 SubAgentRegistry를 직접 사용(ToolRegistry 없음).
  • Chapter 5 — 동일 역할 키를 ToolRegistry + StrategicTool로 감싼 StrategicAnalysisAgentToolOrchestrator, HTTP 래핑은 StrategicAnalysisAgentToolTaskService.
  • Chapter 6 — Task tool, Markdown 서브에이전트 같은 런타임 쪽 이야기로 넓어집니다.
  • Chapter 7 — 같은 역할을 DAG 노드로 쪼개서 엔진이 돌리고, 레지스트리 아이디어는 그대로 재사용합니다.
  • Chapter 8 — 동일 DAG를 YAML(DSL)로 정의하고 YamlDagWorkflowEngine이 실행하는 선언적 워크플로.
  • Chapter 9 — 엔진·DSL 어휘는 Ch8과 동일, 확장은 YAML만. chapter9/dagworkflow/*.yml 로딩 직후 WorkflowDefinitionValidator로 스케줄링 전 선언 오류를 걸러 내는 검증층이 본질인 Validated Agent Workflow DSL.
