과정 요약

본 과정은 Spring AI 기반으로 GPT, Gemini, LLaMA를 전략적으로 조합하여 Multi-LLM 아키텍처와 Orchestrated Multi-Agent 시스템을 실무 수준에서 설계하고 구현하는 고급 과정입니다.

RAG·검색 Tool · Main/Sub(수집·요약) · Task(온보딩 1건) · YAML(단계·담당 선언)

고객지원카톡·메일로 들어온 환불 문의·주문번호·프로모션 예외 정책 — 동일 건인지 묶고 표준 답·에스컬 기준을 정해 달라.

Routing 워크플로(채널·정책 분기) · 멀티 에이전트(분류·답안·검토) · Task·SSE·Redis(동일 건 매칭·진행·Pub/Sub) · Fallback(모델·경로 전환)

개발·연동레거시 API 스펙·모바일 화면 정의·에러 로그 — 누락 필드와 브레이킹 가능성을 표로 대조해 달라.

Tool(스펙·로그 파싱·대조) · Evaluator-Optimizer(차이 검토·수정 루프) · DAG(검증·대조 파이프라인) · 검증 DSL(필드·참조 무결성)

  • 1단계 · Multi LLM 라우팅 + 워크플로·오케스트레이션·협업 패턴

    GPT·Gemini·Llama 등 여러 LLM을 두고, 요청 유형·비용·지연·보안·가용성에 맞게 고르는 라우팅과 Fallback·Router·보안 분기로 단일 모델 의존과 장애 단일점을 줄입니다.

    Spring AI Effective Agents·Anthropic Building Effective Agents가 말하는 단순한 추상화·명시적 구성(composability)을 바탕으로 Chain·Parallel·Routing·Orchestrator-Workers·Evaluator-Optimizer 다섯 패턴을 정리하고, 워크플로·오케스트레이션·전략·정밀·투표 등 협업까지 이어 이후 장에서 쓸 공통 언어를 갖춥니다.

    연계 Chapter:

    Chapter 1. Multi-LLM Architecture — Fallback·Router·보안 라우팅으로 모델을 선택·전환하고, 운영·규제에 맞는 Multi-LLM 실행 계층을 설계합니다.

    Chapter 2. Agentic Workflow Patterns — 다섯 가지 워크플로 패턴으로 단계·병렬·분기·피드백 루프를 갖춘 실행을 구성하는 법을 익힙니다.

    Chapter 3. Orchestrated Multi-Agent Patterns — 패턴을 서비스 파이프라인·오케스트레이션으로 엮고, 전략·정밀·투표 등 멀티 에이전트 협업을 실습합니다.

  • 2단계 · Orchestrated Multi-Agent Main/Sub Agent + Tool + Task Runtime

    앞 단계의 협업 관점을 코드 구조로 옮기며 Main(Main agent, Orchestrator agent)·Sub(Sub agent, Tool agent 등) 역할, 에이전트 레지스트리, 에이전트 간 통신·컨텍스트·상태 전달로 멀티 에이전트 시스템의 내부 골격을 다집니다.

    LLM은 판단·선택에 두고 DB·API·파일·RAG(지식 검색·근거 문서)까지 Tool 인터페이스·레지스트리·파이프라인으로 실행을 분리합니다. 이어 질문 한 줄이 아니라 Task(업무 한 건)를 맨 위에 두어 Task → Agent → Tool·생명주기·상태를 관리하는 Task Runtime으로 확장하고, Markdown(.md)에 Tool 정의를 두며 TaskTool·Markdown 서브에이전트로 묶습니다. 예제는 HTTP·SSE·진행 표시와 Redis(Pub/Sub·단기 이력)로 단계를 연동합니다.

    연계 Chapter:

    Chapter 4. Multi-Agent Architecture — Main(Main agent, Orchestrator agent)·Sub(Sub agent, Tool agent 등) 역할, 레지스트리, 통신·컨텍스트로 멀티 에이전트 내부 구조를 정리합니다.

    Chapter 5. Tool-Orchestrated Multi-Agent — Tool로 실행을 분리하고, RAG에 해당하는 검색·근거 확보도 실행 층에 둡니다.

    Chapter 6. Task-Orchestrated Multi-Agent — Task 중심 런타임과 md 기반 Tool 정의·TaskTool 등으로 실행을 묶고, HTTP·SSE·Redis로 진행을 확인합니다.

  • 3단계 · DAG Engine + Declarative Definition + Validated DSL

    실행을 방향 비순환 그래프(DAG)로 명시하고, 노드·의존성에 따라 병렬·분기·실패 처리를 엔진이 맡는 DAG(Directed Acyclic Graph)기반 워크플로 실행을 둡니다.

    코드에 그래프를 직접 조립하지 않고 YAML 등 구성 파일에 노드·의존·바인딩을 선언적 DSL로 두면 정의와 실행 엔진이 분리됩니다. 로딩 직후 스키마·참조 무결성·순환 의존(사이클)·필수 필드를 검증하는 층을 두어, 스케줄링에 들어가기 전에 선언 오류를 걸러 검증된 DSL로 운영 신뢰도를 높입니다.

    연계 Chapter:

    Chapter 7. DAG-Orchestrated Multi-Agent — DAG와 엔진으로 그래프 실행·스케줄링과 병렬·분기·실패 처리를 구현합니다.

    Chapter 8. Declarative Agent Workflow with YAML — 워크플로를 YAML 등에 선언하고 엔진이 읽어 그래프를 해석·실행합니다.

    Chapter 9. Validated Agent Workflow DSL — 정의 로딩 직후 스키마·참조·사이클 등을 검증해 오류를 조기에 드러냅니다.

위 3단계를 거치면 라우팅·워크플로에서 시작해 검증 가능한 선언적 워크플로까지 이어지는, 확장 가능하고 운영 가능한 AI 시스템 아키텍처를 목표로 완성합니다.

Appendix A. React Front-End & REST Integration (Thymeleaf 실습을 React·REST API로 확장하기). Chapter 1~9 본 흐름은 Spring MVC + Thymeleaf로 서버 렌더링·실습을 이어 갑니다. 부록 A에서는 화면·인터랙션을 React(프론트)로 나누고, Spring Boot를 JSON·REST 중심 백엔드로 두는 전형적인 분리를 실습해 봅니다. Browser ↔ React 개발/호스팅(예: Vite·Node) ↔ Spring AI·REST API 구성으로, 위 「React 시스템 구성도」에 맞춰 프록시·API 호출·CORS·세션/토큰 등 운영에서 자주 쓰는 이슈를 짚는 확장 모듈입니다.

Appendix B. MCP Integration (Model Context Protocol로 Tool·에이전트 런타임 연동하기). Chapter 5~6에서 다룬 ToolRegistry·Task·에이전트 런타임(HTTP·SSE 등)을 전제로, 툴과 컨텍스트를 표준 프로토콜로 노출·소비하려는 시도를 다룹니다. MCP Server / MCP Client 역할, STDIO(표준 입출력)·HTTP 전송, 기존 앱과의 경계(어디까지를 MCP로 뺄지)를 연동·재구성 관점에서 정리합니다. 본편 3단계(라우팅~선언·검증 워크플로) 뒤에, 팀·제품이 요구하는 외부 툴 생태계와 맞닿는 확장으로 보시면 됩니다.

이 확장 로드맵은 기술을 차례로 쌓는 순서이면서, 동시에 프롬프트 몇 줄로 데모를 만드는 수준을 넘어 운영·확장을 전제로 한 시스템 설계를 요구합니다. 그 관점에서 본 과정은 단순히 AI 기능을 하나씩 붙이는 방법이 아니라, 3단계 확장 로드맵에 맞춰 아래 세 가지를 함께 다룹니다.

  • 1단계 — Multi-LLM 라우팅과 워크플로·오케스트레이션·협업 패턴을 아우르는 실행·모델 선택 설계 방법
  • 2단계 — Main/Sub Agent·Tool·Task Runtime으로 복잡한 업무를 모듈화하고 실행을 쌓는 설계 방법
  • 3단계 — DAG Engine·Declarative Definition·Validated DSL로 그래프 실행과 구성·신뢰를 다루는 워크플로 설계 방법

정리하면, 본 과정은 LLM API를 한 번 연동하거나 프롬프트만 다듬는 수준이 아니라, 비용·지연·가용성·보안·규제를 전제로 Multi-LLM 라우팅·에이전트·워크플로·Tool·Task·DAG·선언적 DSL·검증을 하나의 실행 아키텍처로 엮고, 운영·장애·확장 시나리오까지 검토·문서화할 수 있는 현장 설계 역량을 기르는 데 초점을 둡니다.

수강 이후 기대 역할

본 과정을 마치면 현장에서 LLM·에이전트·워크플로를 한데 묶는 AI 시스템 아키텍처를 설계·검토·설명할 수 있는 실무 기반을 갖추게 됩니다. 단일 모델 API 연동이나 프롬프트 작성에 머무르지 않고, 모델 라우팅·멀티 에이전트 오케스트레이션·Tool·Task·DAG·선언적 워크플로·검증까지 연결해 요구사항을 구조화할 수 있는 AI 시스템·플랫폼 설계 관점의 전문가로 성장하는 것을 목표로 합니다.

현장에서 다룰 수 있는 작업 예시

  • 비용·지연·보안·가용성을 고려한 Multi-LLM 운용 전략과 Fallback·라우팅 체계 수립·기술 검토
  • 복잡한 업무를 워크플로·에이전트 협업으로 분해하고, Tool·Task·DAG·선언적 정의 중 어떤 실행 모델이 맞는지 판단·제안
  • 에이전트형 자동화·분석 파이프라인의 아키텍처 설계, 운영·확장·장애 시나리오를 포함한 검토
  • 선언적 워크플로·DSL 도입 시 정의와 실행의 분리, 로딩 단계 검증·거버넌스 방향을 문서화하고 이해관계자와 조율

즉 프롬프트 튜닝·단일 모델 API 연동에 머무는 역할이 아니라, 라우팅·에이전트·워크플로·Tool·Task·DAG·선언적 DSL까지 포함한 실행 경로와 비용·지연·가용성·보안·규제 같은 운영 한계를 함께 설계·검토하고, 그 결과를 제품·플랫폼·보안·운영 이해관계자와의 논의에서 근거·트레이드오프와 함께 전달할 수 있는 위치를 지향합니다.

Chapter 1. Multi-LLM Architecture(다중 모델 전략과 엔터프라이즈 AI 아키텍처 설계)

1. 개념 설명

Multi-LLM Architecture는 모델 개수 늘리기가 아니라, "무조건 한 주소로 보낸다"가 아니라 요청마다 규칙을 정해 보낸다는 뜻에 가깝습니다. 보안·비용·속도·품질을 보며 어느 회사·어느 모델로 보낼지 정하고, 안 되면 다른 모델로 넘길지(Fallback)까지 코드로 밝혀 둡니다.

실무에서는 흐름을 요청 분류 → 정책(보안 등) → 라우팅 → 모델 호출 → 결과 정리처럼 나누고, 어떤 요청이 어떤 경로로 갔는지 나중에 다시 볼 수 있게 남기는 연습을 합니다. "프롬프트 한 방"이 아니라 추적 가능한 호출이 목표입니다.

2. 내부 기술 설명

1) Fallback

엔터프라이즈에서는 정확도만큼 가용성이 중요합니다. 주 모델·보조 모델, 장애·타임아웃 시 전환, 재시도 정책을 묶어 단일 모델 장애가 서비스 전체를 멈추지 않게 합니다.

2) Router

요청을 이해한 뒤 요청 유형·비용·정확도·복잡도·지연 등 기준으로 적절한 모델로 보내는 의사결정 계층입니다. 단순 분기문이 아니라 서비스 정책이 드러나는 층입니다.

3) 보안 기반 라우팅

입력 분석·민감 정보 판단 후 내부(온프레미스 등) 모델과 외부 API 모델 중 어디로 보낼지 정합니다. 데이터 주권·규제 요구에 맞춘 보안 중심 라우팅입니다.

3. 이전 Chapter와 무엇이 다른가

과정 안에서의 선행 Chapter는 없습니다. 다만 흔한 "단일 LLM 한 번 호출" 관행과 비교하면, Chapter 1은 호출 직전까지의 계층(라우팅·Fallback·보안 분기)을 아키텍처로 열어 두는 것이 차이입니다. 이후 Chapter 2부터는 이 위에 워크플로·에이전트·실행 구조를 쌓습니다.

4. 왜 중요한가

모델이 늘어날수록 운영·비용·보안 이슈가 커집니다. Multi-LLM Architecture는 장기적으로 교체·확장·감사 가능한 AI 서비스를 만들기 위한 바닥입니다.

5. 장점

  • 비용·지연·품질의 균형 조절
  • 장애·한도 대응으로 안정성 확보
  • 보안·규제에 맞는 모델 선택
  • 모델 교체 시 상위 설계를 크게 흔들지 않음

6. 난이도

  • 라우팅·Fallback·보안 정책 설계 부담
  • 조합·시나리오 테스트가 많아짐
  • 운영 모니터링·알림 체계 필요

Chapter 2. Agentic Workflow Patterns(실무에서 사용하는 5가지 Agent Workflow 패턴)

1. 개념 설명

Agentic Workflow는 LLM을 질문 한 번·답 한 번으로만 쓰지 않고, 여러 단계를 밟게 짜는 방식입니다. 앞 단계 결과를 다음 단계에 넘기기도 하고, 동시에 여러 갈래를 돌리거나, 조건에 따라 다른 길로 가거나, 평가했다가 다시 고치기 같은 반복도 넣을 수 있습니다.

Chapter 1이 "어느 모델로 보낼지"에 가깝다면, Chapter 2는 "여러 번 호출을 어떤 순서·모양으로 묶을지"입니다. Chain·Parallel·Routing·Orchestrator–Workers·Evaluator–Optimizer 다섯 패턴이 그 레시피 역할을 합니다.

2. 내부 기술 설명

1) Chain — 작업을 순차적으로 이어 실행합니다.

2) Parallel — 독립적인 부분을 동시에 돌려 지연을 줄이거나 근거를 넓힙니다.

3) Routing — 요청 유형·조건에 따라 서로 다른 하위 흐름으로 나눕니다.

4) Orchestrator–Workers — 한 축이 전체를 조율하고, Worker가 부분 작업을 수행하는 역할 분리형 흐름입니다.

5) Evaluator–Optimizer — 생성 → 평가 → 수정·재실행을 반복해 품질을 끌어올립니다.

3. 이전 Chapter와 무엇이 다른가

Chapter 1은 어떤 LLM으로 보낼지(라우팅·Fallback·보안)에 가깝습니다. Chapter 2는 그 위에서 여러 단계의 추론·실행을 어떤 패턴으로 조합할지를 다룹니다. 즉 "모델 선택" 다음 단계인 "실행 레시피"에 해당합니다.

4. 왜 중요한가

실무 난이도가 높은 요청은 한 번의 프롬프트로 끝나기 어렵습니다. 패턴을 알면 복잡한 업무를 설계 가능한 워크플로로 쪼갤 수 있습니다.

5. 장점

  • 정확도·완결성을 단계적으로 확보
  • 자동화·반복 업무에 적합한 골격
  • 팀이 같은 언어로 흐름을 논의하기 쉬움

6. 난이도

  • 패턴 선택·경계 설계가 어려움
  • 단계가 늘수록 디버깅·관측 부담

Chapter 3. Orchestrated Multi-Agent Patterns(Multi-Agent 구조를 실제 서비스 파이프라인으로 구현하기)

1. 개념 설명

Orchestrated Multi-Agent는 에이전트를 많이 늘리자가 아니라, 여러 에이전트가 한 업무를 같이 처리할 때 누가 먼저·누가 나중·언제 합칠지를 한 축에서 조율한다는 뜻에 가깝습니다. Chapter 2에서 배운 워크플로를, 실제 서비스에서 여러 번 부르고 결과를 합치는 파이프라인으로 옮겨 봅니다.

실습에서는 문제 성격에 따라 전략형·정밀형·투표형처럼 협업 모양을 고르는 연습을 하고, Auto Pattern Routing으로 질문만 넣어 적합한 형을 자동 선택하는 진입점도 다룹니다. 핵심은 "몇 개냐"가 아니라 역할과 결과를 어떻게 나누고 합칠지입니다.

2. 내부 기술 설명

1) 전략 분석형(Strategic Analysis)

문제 파악·전략 수립·검증·통합 등 분석·기획에 가까운 단계를 에이전트로 나누어 순차·협업으로 처리합니다.

2) 정밀 실행형(Precision Execution)

분석 → 실행 → 검증 → 수정을 반복해 정확도가 민감한 작업에 맞춥니다.

3) 투표·다중 분석형(Voting Analysis)

동일 문제에 대해 여러 에이전트가 병렬로 의견을 내고 합의·선택 규칙으로 최종안을 고릅니다.

4) 자동 패턴 라우팅(Auto Pattern Routing)

한 번의 질문 입력으로 전략·정밀·투표 중 적합한 파이프라인을 분류해 위임합니다. Chapter 2 Routing을 완성형 패턴 선택에 적용한 예입니다.

3. 이전 Chapter와 무엇이 다른가

Chapter 2는 Chain·Parallel 등 일반적인 워크플로 패턴을 제시합니다. Chapter 3은 그 위에서 "여러 에이전트가 동시에 존재할 때" 서비스 파이프라인 관점에서 어떤 협업 형태(전략·정밀·투표)를 쓸지 고르는 단계입니다. Chapter 4는 다시 그 협업을 Main(Main agent, Orchestrator agent)와 Sub(Sub agent, Tool agent 등)의 역할 분리와 통신 구조로 정교화합니다.

4. 왜 중요한가

단일 에이전트 대화로는 깊이·신뢰도가 부족한 도메인이 있습니다. 오케스트레이션된 멀티 에이전트는 분석·의사결정형 시스템을 현실적으로 만들 수 있는 출발점입니다.

5. 장점

  • 전문 역할 분리로 품질·안정성 향상
  • 문제 유형별로 검증된 협업 형태 선택 가능

6. 난이도

  • 에이전트 수·호출이 늘면 비용·지연 증가
  • 합의·충돌 처리 규칙 설계 필요

Chapter 4. Multi-Agent Architecture (SubAgent 분리 전략과 Agent Registry 내부 구조)

1. 개념 설명

Chapter 3에서는 여러 에이전트가 한 업무를 조율하는 파이프라인과, 문제에 따라 고르는 전략형·정밀형·투표형 같은 협업 모양을 다뤘습니다. 핵심이 "에이전트를 많이 두는 것"이 아니라 역할을 나누고 결과를 어떻게 합칠지에 있었다는 점을 기억하면 Chapter 4가 잘 이어집니다.

Chapter 4의 Multi-Agent Architecture는 그 협업 그림을 코드가 그대로 따라갈 수 있게 Main(Main agent, Orchestrator agent)·Sub(Sub agent, Tool agent 등)으로 역할·책임 경계를 나누고, 오케스트레이션 축에서 흐름을 맞추는 설계입니다.

에이전트끼리 "알아서 같은 정보를 공유하겠지"처럼 말로만 맡기지 않습니다. 메시지·맥락(컨텍스트)·상태는 팀이 정한 규칙대로만 넘기게 코드에 고정합니다. 누가 무엇을 호출하고 무엇을 넘기는지를 레지스트리(이름표에 올려 두고 꺼내 부르기)와 호출 계약(부를 때 지켜야 할 약속) 수준까지 밝혀 두어야, 앞 장의 협업·파이프라인이 실제 서비스 골격으로 안정적으로 남습니다.

2. 내부 기술 설명

1) Main(Main agent, Orchestrator agent)와 오케스트레이션

Main(Main agent, Orchestrator agent)는 단순 응답 주체가 아니라 전체 흐름을 맞추는 오케스트레이션 계층에 가깝습니다. 요청 분석, 전략 선택, Sub(Sub agent, Tool agent 등) 선택·순서 제어, 결과 통합, 재시도 여부 판단 등을 한 축으로 묶습니다.

2) Sub(Sub agent, Tool agent 등)와 역할 단위

Sub(Sub agent, Tool agent 등)는 범용 에이전트가 아니라 한 가지 역할에 집중하는 실행 단위입니다. 분석, 요약, 코드 생성, 검증, 도메인 전문 행위 등으로 쪼개면 변경 범위와 테스트 단위가 줄어듭니다.

과정에서는 날씨·외부 API처럼 Tool·함수 호출이 중심인 Sub를 Tool agent로 짚어 설명합니다. 괄호의 등에는 라우팅·요약처럼 LLM 호출만으로 역할을 나눈 Sub도 포함됩니다.

3) 에이전트 간 통신

멀티 에이전트에서 위험한 것은 암묵적 상태 공유입니다. 결과 전달, 컨텍스트 공유, 상태 전달, 최종 통합 규칙을 구조로 명시해야 합니다.

3. 이전 Chapter와 무엇이 다른가

Chapter 3은 여러 Agent를 한 실행계로 묶는 오케스트레이션 관점과, 전략·정밀·투표 등 문제 유형별 협업 패턴에 초점을 둡니다. "어떤 흐름으로 협업할 것인가"에 가깝습니다.

Chapter 4는 그 위에서 Main(Main agent, Orchestrator agent)와 Sub(Sub agent, Tool agent 등)의 역할·책임과 통신·컨텍스트를 아키텍처 용어로 고정합니다. 패턴 목록이 아니라 멀티 에이전트 시스템의 골격을 다루는 장입니다.

4. 왜 중요한가

협업 패턴만으로는 복잡한 서비스가 금방 엉키고, 확장 시 비용이 커집니다. 역할 경계가 분명한 구조가 있어야 팀 단위로 나눠 맡고 안정적으로 운영할 수 있습니다.

5. 장점

  • 모듈 교체·확장이 쉬움
  • 책임이 분명해 유지보수에 유리
  • 단계별로 정확도·안정성을 끌어올리기 좋음

6. 난이도

  • 설계·디버깅 난이도가 높음
  • 실행 흐름이 복잡해질 수 있음

Chapter 5. Tool-Orchestrated Multi-Agent(Tool을 이용한 실행 레이어 분리 아키텍처)

1. 개념 설명

Tool-Orchestrated Architecture는 생각·판단은 LLM·에이전트에 두고, DB·API·파일·검색(RAG)처럼 밖 세계를 건드리는 일은 전부 Tool이라는 문으로만 나가게 하는 구조입니다. 그러면 권한·로그·재시도를 Tool 주변에만 모아 두기 쉽습니다.

RAG도 문서를 찾는 일은 LLM 속에 숨기지 말고 검색 Tool로 빼는 편이 좋습니다. Java 오케스트레이터가 "지금 검색"을 호출하게 하고, Tool이 문서 조각을 넘기면 모델은 가져온 글을 읽고 답에 집중합니다. 어떤 검색이 있었는지가 로그에 남아 나중에 따라가기도 쉽습니다.

2. 내부 기술 설명

1) 추론(판단)과 실행(Tool) 나누기

오케스트레이터·LLM·Agent 쪽에서는 다음 단계가 무엇인지, 어떤 Tool을 부를지, 인자에 무엇을 넣을지를 정합니다. 그리고 HTTP·DB·파일·검색(RAG)처럼 시스템에 흔적을 남기거나 외부 근거를 가져오는 일은 Tool 호출이라는 같은 관문으로만 나가게 두면, 허용 주체·호출 기록·재시도·타임아웃을 Tool 축에만 모아 적용하기 쉽습니다.

2) Tool 인터페이스·레지스트리·SubAgent

Tool은 이름만 있는 함수가 아니라 입력·출력·실패가 정해진 실행 모듈에 가깝습니다. ToolRegistry에 등록해 두고 이름으로만 부르면 팀 전체가 같은 방식으로 씁니다.

실습에서는 Tool 안에서 Chapter 4의 SubAgentRegistry로 Sub·SubAgent를 다시 불러 역할별 LLM을 쓰기도 합니다. 그러면 바깥은 Tool 로그로 통제하고, 안쪽은 SubAgent로 추론을 나눈 Chapter 4 그림을 그대로 쓸 수 있습니다.

3) 기존 시스템 연동

DB·API·검색·파일처럼 다른 시스템과 붙는 코드를 Tool 뒤로 모으면, 고칠 때도 Tool 단위로 모이고 테스트·로그 패턴도 맞추기 쉽습니다. RAG도 검색 단계를 Tool로 쪼개 두면 무엇을 조회했는지 따라가기 좋고, 권한·개인정보도 API처럼 다루기 쉽습니다.

4) 시스템 메시지(지시문)와의 분리

실행이 Tool로 정리되면 말투·금지 주제·출력 형식 같은 규칙은 시스템 프롬프트만 바꿔도 빠르게 실험할 수 있습니다. 지시문과 Tool 코드·URL을 서로 독립적으로 바꾸기 좋아집니다.

3. 이전 Chapter와 무엇이 다른가

Chapter 4는 Main(Main agent, Orchestrator agent)가 흐름을 잡고 Sub(Sub agent, Tool agent 등)·SubAgentRegistry로 역할을 나누는 멀티 에이전트 골격에 가깝습니다. 다만 DB·API처럼 시스템을 직접 건드리는 코드가 에이전트 쪽에 남기 쉽습니다.

Chapter 5는 단계 순서는 Java 오케스트레이터가 밟고, 부작용 큰 실행은 Tool로만 빼어 감사·권한의 바깥 테두리를 Tool에 둡니다. 필요하면 Tool 안에서 다시 SubAgent를 호출해 Chapter 4의 역할별 LLM을 쓰므로, Tool 로그로 바깥을, SubAgent로 안쪽 추론을 나눠 보기 좋습니다.

4. 왜 중요한가

실서비스에서 LLM이 쓴 문장만으로는 "주문·갱신·환불이 실제로 있었는지"를 나중에 증명하기 어렵습니다. 감사(Audit)에는 어떤 Tool이 어떤 입력으로 호출됐는지가 기록으로 남는 것이 중요하고, Tool 안에서 SubAgent를 썼다면 역할 키·모델 경로까지 이어서 보면 원인 파악이 쉬워집니다. 이렇게 추적 가능한 실행 경로를 갖추는 것이 자동화와 규제 대응의 출발점입니다.

데이터베이스·RAG처럼 모델 파라미터 밖의 사실을 쓰려면, 조회 경로를 Tool 호출로 고정해 두는 편이 검증·감사·장애 분석에 유리합니다. RAG는 보통 검색 Tool → 생성으로 쪼개 두는 경우가 많습니다.

5. 장점

  • 업무 자동화와 시스템 통합
  • Tool 단위 테스트·모니터링
  • 확장과 안정성의 균형

6. 난이도

  • Tool 설계·권한 모델 부담
  • 실행 실패·재시도·타임아웃 설계 필요

Chapter 6. Task-Orchestrated Multi-Agent(TaskTool 기반 Agent Runtime 설계)

1. 개념 설명

Task-Orchestrated Architecture는 채팅 한 줄이 아니라 업무 한 건(Task)을 잡고, 시작 → 진행 중 → 끝(또는 실패)처럼 상태를 앱이 계속 따라가게 짜는 관점입니다. 그래야 화면에 진행을 보여 주거나, 중간에 멈췄다가 이어 하거나, 나중에 감사할 때도 남는 정보가 생깁니다.

실습에서는 Spring AI 커뮤니티 agent-utils의 Agent Runtime 골격 위에서 생각 → 행동 → 관찰 루프·상태 저장·서브에이전트·할 일 목록을 묶습니다. TaskTool로 한 요청의 흐름을 묶고, SSE·Redis로 진행을 보여 주는 데 집중합니다.

2. 내부 기술 설명

1) Task를 맨 위 단위로 둔다

Task는 채팅 한 줄과 같은 레벨이 아니라, 처리해야 할 업무 한 건에 붙는 꼬리표(식별자)에 가깝게 생각하면 쉽습니다. 그 업무가 지금 어디까지 왔는지·끝났는지를 런타임이 기록해 두면, 화면에 진행 상황을 보여 주거나 나중에 이어 하기가 가능해집니다.

2) 생명주기(상태)

만들어짐 → 기다림 → 실행 중 → 완료(또는 실패)처럼 단계 이름을 정해 두면, 운영 화면·알람·로그가 같은 언어로 맞춰집니다. 나중에 실패한 건만 다시 돌리기, 재시도 규칙을 붙이기도 수월해집니다.

3) Task → Agent → Tool

한 Task 안에서 Sub(Sub agent, Tool agent 등)를 고르고, Tool을 부르고, 중간 결과를 쌓고, 끝났는지를 판단하는 흐름을 한 덩어리로 묶습니다. 그러면 Chapter 4~5에서 배운 역할 분리·Tool 실행이 "업무 한 건" 기준으로 정리됩니다.

실습에서는 TaskTool로 모델이 도구를 타고 들어가고, Markdown(.md)에 적어 둔 서브 에이전트를 이름으로 부르며, agent-utils가 제공하는 Agent Runtime 골격 위에서 이 레이어를 조립하는 흐름을 다룹니다.

3. 이전 Chapter와 무엇이 다른가

Chapter 5는 "어떤 Tool을 어떤 순서로 부를지"를 Java 오케스트레이터 코드에 적어 두는 것에 가깝습니다. LLM이 마음대로 순서를 바꾸지 않습니다.

Chapter 6은 그 실행을 업무 ID·Task에 걸어 묶고, TaskTool·StrategicWorkflowContext(워크플로 컨텍스트)·TodoWrite 등으로 진행·할 일·상태를 두껍게 만든 뒤, 같은 흐름을 SSE로 화면에 흘려 보낼 수 있게 합니다. 즉 "무엇을 실행할지"에 더해 "사용자·운영자가 중간 상황을 어떻게 볼지"가 과제에 포함됩니다.

4. 왜 중요한가

실제 서비스에서는 답변 텍스트만이 아니라 처리 중인 건이 남고, 중간에 멈추면 이어하기, 잘못되면 다시 돌리기, 나중에 감사가 필요합니다. Task를 두면 이런 요구를 상태와 ID로 표현하기 쉬워져, "챗 한 번"으로는 부족한 제품 요구에 맞출 수 있습니다.

5. 장점

  • 업무 자동화와 실행 흐름 관리
  • 상태 기반 모니터링·재처리
  • 확장 시에도 업무 경계가 유지됨

6. 난이도

  • 상태 설계·동시성·일관성 부담
  • 실행 흐름이 길어지면 복잡도 증가

Chapter 7. DAG-Orchestrated Multi-Agent(엔터프라이즈급 DAG(Directed Acyclic Graph)기반 AI Workflow 설계)

1. 개념 설명

DAG-Orchestrated Architecture는 업무 단계를 상자(노드)와 화살표로 그린 작업 순서도에 가깝게 두는 방식입니다. DAG는 "화살표를 따라가도 제자리로 돌아오는 루프가 없다"는 뜻이라, 언젠가 끝나는 흐름을 수학적으로 맞추기 쉽습니다. 워크플로 엔진이 "A가 끝나야 B", "C와 D는 동시에 돌려도 됨" 같은 규칙을 지키며 돌립니다. Agent·Tool·Task는 그대로 쓰되, 먼저 그림(그래프)으로 순서를 밝혀 둔다는 점이 앞 장과 다릅니다.

2. 내부 기술 설명

1) DAG가 의미하는 것

화살표는 "이 단계 결과가 저 단계에 필요하다"는 의존 관계입니다. 서로 기다릴 필요가 없는 상자끼리는 동시에(병렬) 돌릴 후보가 됩니다. 루프가 없으면 엔진이 끝날 순서를 안정적으로 잡을 수 있습니다.

2) 노드와 엔진

노드 한 칸은 라우팅·분석·Tool 호출·병합·평가처럼 실제로 한 번 실행되는 단위입니다. 엔진은 "지금 돌려도 되는 노드"만 골라 돌리고, 실습 코드에서는 분기·실패 시 멈춤·평가/최적화 루프처럼 자바에 적어 둔 정책을 따릅니다. (노드마다 범용 재시도 큐를 다는 것은 이 과정 범위 밖 확장 주제입니다.)

3) 의존성 기반 실행

예를 들어 두 분석이 끝나야 병합이 돌아가고, 서로 안 기다리는 단계는 병렬로 돌릴 수 있습니다. 어딘가가 실패하면 그 뒤 단계를 건너뛰거나 전체를 오류로 마감하는 식으로 정할 수 있고, 구현에 따라 일부는 빈 값을 채워 다음으로 넘기기도 합니다.

3. 이전 Chapter와 무엇이 다른가

Chapter 4~6까지는 "누가 무엇을 할지"는 잡혀 있어도, 전체 순서·분기가 오케스트레이터·런타임·대화 코드 여기저기에 흩어지기 쉽습니다.

Chapter 7은 그 순서를 한 장의 그래프로 밝혀 두고 엔진이 지키게 합니다. 나중에 같은 그림으로 다시 돌려 보기(재현)하거나 병렬을 정확히 통제하려는 단계라고 보면 됩니다.

4. 왜 중요한가

단계가 늘수록 "먼저 뭐 했더라?"가 머릿속·코드 속에만 있으면 깨지기 쉽습니다. DAG로 누가 누구 결과를 쓰는지를 밖으로 꺼내두면, 장애 때 어디부터 다시 볼지 잡기 쉽습니다.

5. 장점

  • 많은 단계도 한눈에 보이는 그림으로 정리할 수 있음
  • 서로 안 기다리는 단계는 동시에 돌려 시간·자원을 아낄 수 있음
  • 운영·감사에서 같은 순서로 다시 실행하기 쉬움

6. 난이도

  • 처음엔 그래프를 어떻게 쪼갤지 설계가 부담스러울 수 있음
  • 엔진이 실패·분기를 어떻게 처리하는지 익숙해져야 함

Chapter 8. Declarative Agent Workflow with YAML(YAML 기반 DAG 정의와 실행 엔진 분리)

1. 개념 설명

Declarative Agent Workflow with YAML은 "단계와 순서"를 자바 코드에 한 줄씩 또 적지 않고, YAML 파일에 정해진 형식(DSL)으로 적어 두는 방식입니다. 무엇을 돌릴지(정의)는 문서가 말하고, 읽어서 실제로 돌리는 법(엔진)은 프로그램이 맡깁니다. 흐름을 바꿀 때 엔진을 자주 배포하지 않고 파일만 고칠 수 있다는 점이 핵심입니다.

2. 내부 기술 설명

1) DSL로 그래프 적기

노드 이름, 누구 뒤에 실행할지, when 같은 분기, eval-opt-loop 같은 반복 블록을 정해진 필드에 적습니다. 엔진이 리소스(resources) 디렉터리 아래에 둔 YAML(.yml) 정의를 읽어 순서를 정한 뒤 노드를 실행하는 형태입니다. (이 예제 범위에서는 노드 단위 동시(병렬) 스케줄까지는 다루지 않습니다. 의존 관계에 따라 여러 노드를 동시에 돌리는 실행은 자바 코드로 DAG를 조립하는 흐름과 대조하면 됩니다.)

2) 로더와 실행 엔진

로더가 YAML을 읽어 내부 구조로 바꾸고, 실행 엔진이 그 구조를 보고 돌릴 노드를 고릅니다. Chapter 7과 비슷하게 의존성이 풀린 것부터 실행하되, 어떤 노드를 넣었는지는 YAML이 먼저입니다.

3) 운영·버전

워크플로 파일을 앱 코드와 다른 브랜치·저장소에 둘 수 있고, 개발/운영마다 다른 YAML을 고르기도 쉽습니다. 문제가 나면 파일만 이전 버전으로 되돌려 롤백할 수 있습니다.

4) 실행 엔진 분리 패턴

정의 로더·실행 엔진·노드 핸들러를 나누면, YAML만 바꿔 같은 엔진으로 여러 그래프를 돌리기 쉽습니다. (Chapter 8 본문 1. 개념 정리 안의 실행 엔진 분리 패턴과 같은 주제입니다.)

5) 요청 시점의 워크플로 정의 바인딩

요약: 엔진은 한 벌로 두고, 요청마다 "이번에 쓸 DSL(YAML) 정의"만 이름(식별자)으로 고르면 같은 진입으로 여러 그래프를 태울 수 있습니다. 자주 바뀌는 "무엇을 돌릴지"는 문서에, "어떻게 읽고 순서를 지킬지"는 엔진에 두면 변경·배포·감사를 나누기 쉽습니다. 필요성·효과·실습 연결은 Chapter 8 본문 5. 요청 시점의 워크플로 정의 바인딩 절에서 자세히 다룹니다.

3. 이전 Chapter와 무엇이 다른가

Chapter 7은 그래프를 자바 코드로 조립하는 비중이 큽니다.

Chapter 8은 그 내용을 YAML 문서로 옮깁니다. 흐름만 바꿀 때는 개발자 배포 없이 문서 수정으로 반복하기 좋습니다.

4. 왜 중요한가

현업에서는 "흐름 한 줄 바꾸려면 매번 코드 리뷰"가 병목이 됩니다. 정의(문서)와 실행(엔진)을 나누면, 기획·운영이 문서만 다루고 개발은 엔진·핸들러에 집중하는 식으로 역할과 속도를 나누기 쉽습니다.

5. 장점

  • 흐름만 바꿀 때 YAML만 고치면 되어 반응이 빠름
  • 같은 엔진으로 여러 업무용 워크플로를 파일만 바꿔 운영 가능
  • 개발/운영마다 다른 파일을 쓰기 쉬움

6. 난이도

  • "이 필드는 이렇게 쓴다"는 팀 규칙(DSL)을 맞춰야 함

Chapter 9. Validated Agent Workflow DSL(스키마·의존성 검증으로 신뢰하는 YAML 워크플로 DSL)

1. 개념 설명

Chapter 9는 엔진 코드는 그대로 두고, Chapter 8과 같이 YAML(DSL)로 워크플로를 늘리는 방식은 유지합니다. 여기에 더하는 것은 파일을 읽은 직후, 아직 실행하기 전에 틀린 정의를 걸러 내는 검증 단계입니다.

YAML을 "그냥 설정"이 아니라 워크플로 전용 작은 언어(DSL)로 보면, 오타·없는 노드 참조·순환(루프)·빠진 필수 항목은 전부 나중에 터질 버그입니다. 사용자에게 에러가 나기 전에 로딩 직후에 막아 두는 것이 목표입니다.

2. 내부 기술 설명

1) 로딩할 때 검증 끼워 넣기

YAML을 파싱해 WorkflowDefinition으로 옮긴 다음, WorkflowDefinitionValidator 규칙을 통과시킵니다. (이 과정 예제는 JSON Schema 파일 대신 자바 검증기로 팀 규칙을 고정합니다.) 통과한 정의만 캐시되어 엔진으로 가고, 실패한 정의는 캐시되지 않습니다.

Ch9Controller의 POST /ch9/strategic-analysis도 Chapter 8과 같이 workflowDefinition(기본값 strategic-analysis)으로 이번에 검증·실행할 YAML 정의 id를 넘깁니다. 엔진 동작은 Chapter 8과 같고, 차이는 로딩 직후 검증을 통과한 정의만 해당 id로 캐시·재사용된다는 점입니다.

2) 검증이 잡아 주는 대표적인 실수

  • 노드 이름이 겹치지 않는지, "이 단계는 A 뒤에"라고 적었는데 A가 파일 안에 있는지
  • 화살표를 따라가면 제자리로 돌아오는 순환이 없는지(DAG인지)
  • handler 등 꼭 있어야 하는 필드가 비었는지, eval-opt-loop 안에 필요한 설정이 채워졌는지

한 줄로 말하면 "이 YAML이 우리 팀이 약속한 규칙에 맞는가?"를 실행 전에 묻는 단계입니다. 실제 회사에서는 JSON Schema·CI 린트로 같은 일을 더 강하게 하기도 합니다.

3) 팀·CI와 연결

검증 규칙을 코드·테스트에 박아 두면, 리뷰나 배포 파이프라인에서도 같은 기준으로 반복 검사할 수 있습니다.

3. 이전 Chapter와 무엇이 다른가

Chapter 8은 YAML로 흐름을 적고 엔진이 읽어 실행하는 데 초점이 있습니다.

Chapter 9는 그 앞단에 검증 게이트를 둡니다. 엔진 동작은 같고, 안전한 문서만 통과시키는지가 추가됩니다.

4. 왜 중요한가

문서만 고치면 되는 만큼, 잘못 고친 YAML도 운영 사고로 이어지기 쉽습니다. 검증은 그 사고를 실행 전에 잡고, 팀 전체가 따를 규약(계약)을 코드로 남기는 역할을 합니다.

5. 장점

  • YAML 실수를 사용자가 보기 전·실행 전에 잡을 수 있음
  • 엔진 안에서 "왜 이 단계가 안 돌았지?" 같은 추적이 줄어듦
  • 검증 규칙이 곧 팀 약속서가 되어 협업이 수월해짐

6. 난이도

  • 규칙을 처음 짜고 계속 고치는 일이 따름
  • 특이한 예외까지 전부 규칙으로 표현하려면 점점 복잡해질 수 있음

Appendix A. React Front-End & REST Integration(Thymeleaf 실습을 React·REST API로 확장하기)

1. 개념 설명

Appendix A는 Chapter 1~9에서 다룬 Spring AI·에이전트·워크플로 구현을, 프론트엔드와 백엔드 API의 관심사 분리·배포 단위(아티팩트) 분리에 맞게 옮겨 보는 선택적 확장 모듈입니다. 본 과정 본문은 Spring MVC + Thymeleaf 기반 서버 사이드 렌더링(SSR) 이지만, 운영 시스템에서는 SPA(예: React)가 HTTP 위의 JSON으로 REST 계약을 쓰는 구성이 흔합니다. 본 부록은 템플릿 기반 SSR과 클라이언트 렌더링(CSR) + API 백엔드 사이의 스택·렌더링·전송 계층 차이를 실습으로 맞춰 봅니다.

2. 이 부록에서 정리하는 내용

화면(React)이 담는 역할(상태, 스트리밍 UI, 양식)과, 서버(Spring)가 담는 역할(라우팅·LLM·Tool·Task·세션)을 경계로 나눕니다. REST 엔드포인트 설계, 개발 시 Browser ↔ React 개발 서버 ↔ Spring(REST) 흐름, 운영과 유사한 연결을 위쪽 시스템 구성의 React 다이어그램과 맞춰 봅니다. Thymeleaf에 있던 화면만 쪼개는 수준이 아니라, 응답·오류·진행(SSE) 표현이 프론트·백 어디에 머물지까지 함께 점검하는 것이 목적입니다.

3. 앞선 Chapter들과의 관계

이전 Chapter들에서 Controller는 Multi-LLM·SubAgent·Tool·Task를 한데 묶어, HTTP로 내보낼 대표 행동의 경계를 이미 잡아 온 셈입니다. 부록 A는 여기에 UI를 분리해 React가 화면·상호작용을 맡고, Spring은 REST API Server로 JSON만 내보내는 쪽에 초점을 맞춥니다. Swagger(예: SpringDoc OpenAPI)로 URL·스키마·응답 예시를 박아 두면 React에서 엔드포인트·계약을 읽기 쉬워지고, 실행·오케스트레이션의 설계(Chapter 1~9)는 그대로 연속된다고 보시면 됩니다. 바뀌는 것은 뷰가 Thymeleaf·서버 HTML이 아니라 React + REST 호출이라는 사용 방식에 가깝습니다.

Appendix B. MCP Integration(Model Context Protocol로 Tool·에이전트 런타임 연동하기)

1. 개념 설명

Appendix B는 Model Context Protocol(MCP)을 기존 Spring·에이전트 런타임 위에 두는 통합·확장 계층을 다루는 부록입니다. 본문을 통해 인프로세스(in-process) Tool 등록·호출(예: ToolRegistry 축)을 익힌 뒤, 여기서는 MCP가 정의하는 원시 항목(Tool·Resource·Prompt 등)을 프로세스·런타임 경계 밖으로 노출·협상하도록, 호스트(클라이언트)와 MCP Server의 계약(역할·권한·에러·세션)을 밝히고, STDIO·HTTP(스트리밍 포함) 등 트랜스포트(transport)에 맞춰 엔드포인트·보안·운영을 맞추는 연습을 담습니다.

2. 이 부록에서 정리하는 내용

Chapter 5~6의 ToolRegistry·Task·런타임·스트리밍 맥락 위에서, MCP Server가 어떤 능력(도구·스키마)을 외부에 선언하는지, MCP Client(호스트/앱)가 그걸 에이전트/오케스트레이터에 어떻게 붙이는지 정리합니다. STDIO·HTTP는 다른 런타임·팀과 맞물릴 수 있는 운반 방식으로 두고, 같은 비즈니스 Tool이 앱 안 호출이었는지 MCP이었는지 비교할 수 있게 합니다.

3. 앞선 Chapter들과의 관계

Chapter 5는 Tool을 같은 프로세스에 두는 오케스트레이션이고, Chapter 6은 Task와 런타임으로 긴 흐름을 잡는 축입니다. MCP는 그 ‘툴 연결’을 팀·언어·프로세스 밖으로 열 때 쓰는, 엔지니어링·운영 한 단계로 보면 이어집니다.
