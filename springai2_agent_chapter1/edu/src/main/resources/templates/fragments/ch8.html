Chapter 8. Declarative Agent Workflow with YAML

YAML 기반 DAG 정의와 실행 엔진 분리

본 장은 Chapter 7에서 코드로 직접 구성하던 DAG(Directed Acyclic Graph)를 선언적으로 옮겨 적는 방식으로 다룹니다. 그래프를 서술할 때 쓰는 어휘는 nodes·dependsOn·handler·when·config처럼 워크플로에만 의미가 정해진 키로 모아 두었고, 그 구체적인 표기(문법적 표면)는 YAML 파일입니다. 이런 “작은 전용 언어”를 흔히 DSL(Domain-Specific Language)이라 부릅니다. (이 장에서는 용어와 분리 구조 위주로 짚고, DSL을 무엇으로 볼지·문서를 어떤 규칙으로 검증할지는 Chapter 9에서 훨씬 구체적으로 이어집니다.) 별도의 실행 엔진은 이 DSL 문서를 읽어 노드를 스케줄링하며, 더 이상 “어떤 노드를 언제 실행할지”를 자바 코드로 고정하지 않고 파일에 적힌 노드·간선·조건·루프 설정을 해석해 실행 가능한 노드를 찾아냅니다.

즉 DAG 정의(= DSL로 적힌 YAML)와 DAG 실행 엔진(Java)을 분리해, 워크플로 변경은 DSL 문서(YAML) 수정으로, 실행 스케줄링과 eval-opt-loop 등 루프 처리는 엔진에서 공통화하는 선언적 Agent Workflow 패턴을 구현하는 것이 목표입니다.

  • 정의(Definition) — 노드 이름, 타입, 입력/출력 키, 의존 노드, 루프 조건 등을 classpath:chapter8/dagworkflow/strategic-analysis.yml 같은 YAML 파일(워크플로 DSL 문서)에 선언합니다. 팀은 범용 자바로 그래프를 조립하는 대신, 약속된 필드만으로 그래프를 “씁니다”.
  • 실행(Execution) — YamlDagWorkflowEngine(예시)는 DSL 문서를 파싱해 WorkflowNode(Chapter 7 노드 핸들러)를 조회하고, 위상 순서로 노드를 순차 실행하며 when 분기와 eval-opt-loop 설정을 해석합니다. (Chapter 7 DagWorkflowEngine의 기술·시장 병렬 실행과 달리, 본 예제 엔진은 동시에 여러 노드를 스케줄하지 않습니다.)
  • 확장(Extension) — 새 노드 추가나 분기 조건 변경은 DSL(YAML) 편집으로 가능하며, 엔진은 바뀐 그래프를 같은 규칙으로 그대로 실행합니다.

이 구조를 통해 Chapter 7의 코드 중심 DAG-Orchestrated Multi-Agent를 DSL·YAML 선언 중심의 Declarative Agent Workflow로 한 단계 더 추상화합니다. Chapter 9에서는 엔진·DSL 어휘는 동일하게 두고, 로딩 파이프라인의 검증층(WorkflowDefinitionValidator)으로 잘못된 문서가 스케줄링에 넣기 전에 걸러지는 예시를 이어서 다룹니다. DSL에 대한 개념 정리·검증 규칙 예시·Validator와 필드의 대응 등은 Chapter 9 본문에서 이 장보다 한층 구체적으로 설명합니다.

실무 관점: Airflow, Prefect, Dagster, LangGraph 등 최신 워크플로/에이전트 프레임워크도 공통적으로 “그래프를 서술하는 층(파이썬 DSL, YAML, 전용 API 등)과 실행 엔진”을 나눕니다. 이 장의 예제는 Spring AI 위에서 YAML 표면의 워크플로 DSL과 엔진을 분리해, 그 아이디어를 구현하는 최소 단위에 가깝다고 볼 수 있습니다.

1. 개념 정리 (YAML 기반 DAG 정의)

Chapter 7에서는 DagWorkflowEngine이 내부에서 RouterNode, TechnicalAnalysisNode, MarketAnalysisNode 등을 직접 조합해 DAG를 코드로 표현했습니다. Chapter 8에서는 이 그래프를 YAML로 적힌 워크플로 DSL 정의로 바꿔 적는 것을 목표로 합니다.

YAML은 DSL의 저장 형식이고, 의미 있는 키 집합이 곧 이 과정에서 말하는 DSL입니다. 전략 분석 그래프에 대응하는 전체 YAML 예시(주석 포함)는 이 장 §3와 chapter8/dagworkflow/·chapter9/dagworkflow/ 리소스를 보면 되고, 문서 규칙·검증 관점은 Chapter 9 본문이 담당합니다.

실제 구현에서는 이러한 DSL 구조를 Spring YAML 프로퍼티 또는 별도 YAML 파일로 두고, YamlDagWorkflowEngine이 이를 파싱해 WorkflowNode 실행 계획으로 변환합니다. 이때 handler 값은 Chapter 4·7과 마찬가지로 SubAgentRegistry 키나 Node 핸들러 Bean 이름에 매핑할 수 있습니다.

실행 엔진 분리 패턴

Chapter 7의 DagWorkflowEngine는 “정의 + 실행”을 한 클래스 안에서 담당했습니다. Chapter 8에서는 다음과 같이 세 계층으로 나눠볼 수 있습니다.

  • Definition Loader — YAML을 읽어 WorkflowDefinition 객체로 변환 (YamlWorkflowDefinitionLoader)
  • Execution Engine — 의존성 그래프를 분석해 WorkflowNode 실행 순서를 스케줄 (YamlDagWorkflowEngine)
  • Node Handler — 각 노드 id/type에 해당하는 실제 비즈니스 로직 (RouterNode, TechnicalAnalysisNode 등)

2. 코드 기반 DAG vs YAML 기반 DAG

코드 기반 DAG(Chapter 7)과 YAML(DSL 문서) 기반 DAG(Chapter 8)를 비교하면 다음과 같습니다.

구분 코드 기반 DAG (Ch7) YAML 기반 DAG / DSL 문서 (Ch8)
정의 위치 자바 코드 (DagWorkflowEngine 내부 체인) YAML 파일 — 워크플로 DSL 문서 (workflow/*.yml)
변경 방법 코드 수정 + 빌드/배포 YAML 수정 + 재로딩(또는 배포)
유연성 코드 레벨 커스터마이징은 자유롭지만 구조 변경이 무겁다 워크플로 구조 변경에 유연, 런타임 재구성도 용이
가시성 그래프 구조를 이해하려면 코드를 따라가야 함 YAML만 봐도 노드·분기·의존 관계를 한눈에 파악 가능
검증 컴파일 시 타입 검사가 강력 스키마/유효성 검증 로직을 별도로 설계해야 함

3. YAML DSL 구조 (핵심 개념 정리)

YAML은 단순 설정 파일이 아니라 워크플로를 기술하는 DSL로 보는 것이 맞습니다.

기본 구성 예시

id: strategic-analysis
nodes:
  - id: router
  - id: simple-query
    dependsOn: [router]

핵심 필드 (강의용 축약)

  • 워크플로 메타
    • id — 워크플로 식별자
    • description — 설명 (운영·모니터링용)
  • 노드 정의
    • id — 노드 이름 (의존성 기준)
    • type — 실행 유형 (llm, router, loop 등)
    • handler — 실제 실행 로직 (SubAgent 또는 Bean 매핑)
    • dependsOn — 선행 노드
    • when — 조건 실행
    • outputs — 결과를 컨텍스트에 저장
  • config (노드별 옵션) — 예: loop 노드 
    config:
  maxRounds: 4
  evaluator: report-evaluator
  optimizer: report-optimizer
  approveThreshold: 0.8
    • 반복 횟수 제한
    • 평가·개선 에이전트 지정
    • 승인 기준 설정

전체 예시 (주석 포함)

chapter8/dagworkflow/strategic-analysis.yml 및 chapter9/dagworkflow/strategic-analysis.yml과 같은 구조를, 필드 의미를 한눈에 보기 위해 교육용 주석과 함께 옮긴 것입니다. 

id: strategic-analysis                 # 워크플로 식별자 (컨트롤러/서비스에서 workflowDefinition=... 으로 사용)
description: Strategic analysis workflow (YAML-defined DAG)

nodes:
  # ─────────────────────────────────────────────────────────────
  # 1) Router 노드
  #    - 사용자 입력을 SIMPLE / STRATEGIC 으로 분류
  #    - handler: ch8 WorkflowNode.id() (보통 …-ch8; 노드 내부에서 SubAgent 키는 별도)
  # ─────────────────────────────────────────────────────────────
  - id: router                         # YAML 안에서의 노드 식별자 (dependsOn 에서 참조)
    type: router                       # 노드 유형 (엔진에서는 참고용 메타데이터)
    handler: routing-ch8               # WorkflowNodeRegistry (= WorkflowNode.id())
    outputs:
      routeCategory: route.category    # (예시) 라우팅 결과를 컨텍스트의 route.category 로 매핑한다는 의미적 표현

  # ─────────────────────────────────────────────────────────────
  # 2) SIMPLE 브랜치 — 단일 응답 노드
  #    - Router 결과가 SIMPLE 일 때만 실행
  # ─────────────────────────────────────────────────────────────
  - id: simple-query
    type: llm
    handler: simple-query-ch8          # 노드 내부에서 SubAgent "simple-query" 호출
    dependsOn: [router]                # router 가 끝난 뒤에만 실행 가능
    when: route.category == 'SIMPLE'   # ch8 엔진의 shouldRun 이 해석하는 조건식 (간단한 문자열 비교)

  # ─────────────────────────────────────────────────────────────
  # 3) STRATEGIC 브랜치 — 기술 분석
  #    - Router 결과가 STRATEGIC 일 때만 실행
  # ─────────────────────────────────────────────────────────────
  - id: technical-analysis
    type: llm
    handler: technical-analysis-ch8
    dependsOn: [router]                # router 이후에 실행
    when: route.category == 'STRATEGIC'

  # ─────────────────────────────────────────────────────────────
  # 4) STRATEGIC 브랜치 — 시장 분석
  #    - Router 결과가 STRATEGIC 일 때만 실행
  #    - technical-analysis 와는 서로 dependsOn 이 없으므로 병렬 실행 가능
  # ─────────────────────────────────────────────────────────────
  - id: market-analysis
    type: llm
    handler: market-analysis-ch8
    dependsOn: [router]
    when: route.category == 'STRATEGIC'

  # ─────────────────────────────────────────────────────────────
  # 5) 병합 노드 — 기술/시장 분석 결과를 하나의 초안으로 합치기
  #    - dependsOn 에 technical-analysis, market-analysis 두 개가 있으므로
  #      두 노드가 모두 끝난 뒤에만 실행됩니다.
  # ─────────────────────────────────────────────────────────────
  - id: merge-report
    type: merge
    handler: merge-report-ch8
    dependsOn:
      - technical-analysis
      - market-analysis

  # ─────────────────────────────────────────────────────────────
  # 6) 평가/개선 루프 노드 (개념적 핸들러)
  #    - 예제에서는 하나의 handler(eval-opt-loop) 로 표현했지만,
  #      실제 구현에서는 EvaluationNode / OptimizationNode 조합으로 풀어 쓸 수도 있습니다.
  #    - config 에 루프 설정(최대 회차, evaluator/optimizer 핸들러, 승인 임계값 등)을 둡니다.
  # ─────────────────────────────────────────────────────────────
  - id: eval-opt-loop
    type: loop
    handler: eval-opt-loop             # 이 id 에 맞는 WorkflowNode 를 만들거나, 향후 엔진에서 특별 처리 가능
    dependsOn: [merge-report]
    config:
      maxRounds: 4                     # 최대 평가/개선 반복 횟수 (엔진에서 참조)
      evaluator: report-evaluator-ch8
      optimizer: report-optimizer-ch8
      approveThreshold: 0.8            # 승인 임계값 (예: EvaluationApprovalDecider 에 넘길 값)

4. YAML 스키마 설계 예시

DSL로 DAG를 정의하려면(표기는 YAML이어도) 최소한 다음 정보를 스키마·어휘로 정해 두는 것이 좋습니다.

  • 워크플로 메타데이터: id, description, 버전 등
  • 노드 목록: id, type, handler, dependsOn, when, config 등
  • 전역 설정(설계·확장 시): 타임아웃·노드 재시도·동시 실행 상한 등을 스키마에 둘 수 있음 — 본 과정 예제 엔진은 노드 config(예: eval-opt-loop) 중심

Spring 환경에서는 이 스키마를 @ConfigurationProperties로 바인딩하거나, 전용 YamlWorkflowDefinitionLoader를 만들어 Map<String, WorkflowDefinition> 형태로 적재해 둘 수 있습니다. 이후 YamlDagWorkflowEngine은 workflowId로 정의를 찾아 실행 계획을 구성합니다.

위 예시 YAML에는 워크플로 전체에 대한 메타 정보와 각 노드에 대한 실행 정의가 함께 들어 있습니다. 각 필드는 다음과 같이 해석할 수 있습니다.

  • 워크플로 메타데이터
    • id: 워크플로의 고유 식별자입니다. 예시의 strategic-analysis처럼, 엔진이 어떤 YAML을 불러와야 하는지 구분하는 “워크플로 이름/키”가 들어갑니다. 일반적으로 strategic-analysis, customer-onboarding-v2 같은 영문 슬러그를 사용합니다.
    • description: 워크플로의 용도와 역할을 사람이 읽을 수 있게 설명하는 필드입니다. 실행 로직에는 직접 쓰이지 않지만, 운영·모니터링 화면에서 설명 텍스트로 활용할 수 있습니다.
  • 노드 정의 (nodes 배열 안)
    • id: 각 노드를 구분하는 고유 이름입니다. 예: router, simple-query, technical-analysis 등. dependsOn에서 이 id를 참조해 노드 간 의존 관계를 표현합니다.
    • type: 노드가 어떤 종류의 역할을 하는지 나타내는 노드 타입입니다. 예시에서는 router, llm, merge, loop 등이 있으며, 엔진은 이 값을 기준으로 어떤 Node 핸들러(예: LLM 호출, 라우팅, 병합, 루프 제어)를 써야 할지 결정합니다.
    • handler: 실제로 비즈니스 로직을 수행하는 핸들러의 이름입니다. 예를 들어 simple-query, technical-analysis, market-analysis처럼 작성하며, SubAgentRegistry의 키나 Spring Bean 이름에 매핑됩니다. 즉, 엔진은 handler 값을 통해 “어떤 서브에이전트/노드 클래스”를 실행할지 찾습니다.
    • outputs: 노드 실행 결과 중에서 다음 노드들이 참조할 수 있도록 노출할 값의 매핑입니다. 예시의 routeCategory: route.category는 “라우터 노드의 내부 결과 중 route.category라는 값을, 워크플로 전체 컨텍스트에서는 routeCategory라는 이름으로 쓸 수 있게 한다”는 의미입니다. 이후 노드의 when 조건식에서 route.category 또는 매핑된 키를 사용할 수 있습니다.
    • dependsOn: 이 노드가 실행되기 전에 완료되어야 하는 선행 노드 목록입니다. 예를 들어 dependsOn: [router]라고 적으면, router 노드가 끝난 뒤에만 해당 노드가 실행됩니다. 여러 개를 넣으면 dependsOn: [technical-analysis, market-analysis]와 같이 모든 선행 노드가 완료된 후에 실행됩니다.
    • when: (예시 YAML에는 포함되어 있지만 생략된 부분도 있을 수 있는) 조건부 실행 표현식입니다. route.category == 'SIMPLE'처럼 작성해, 워크플로 컨텍스트 값에 따라 노드를 실행할지 말지를 제어합니다.
  • config 블록 (특정 타입 노드 전용 설정)
    • config: 특정 타입의 노드가 필요로 하는 추가 설정값들을 담는 하위 객체입니다. 예시에서는 loop 타입 노드(eval-opt-loop)가 루프 횟수, 평가/최적화 전략 등을 이 블록에서 읽습니다.
    • maxRounds (config 안): 루프 노드가 최대 몇 번까지 반복할 수 있는지 나타내는 정수 값입니다. 예시의 4는 “최대 4라운드(평가·개선 반복 상한)” 정도로 해석할 수 있으며, 엔진은 이 숫자에 도달하면 더 이상 반복하지 않고 종료/최종 결과를 반환합니다.
    • evaluator (config 안): 현재 보고서(또는 출력물)를 평가하는 평가 노드/에이전트의 식별자입니다. report-evaluator라는 값은 SubAgentRegistry에서 등록된 평가용 서브에이전트, 또는 “평가용 LLM 프롬프트/노드 Bean” 이름에 매핑될 수 있습니다.
    • optimizer (config 안): 평가 결과를 바탕으로 출력을 수정/개선하는 노드/에이전트의 식별자입니다. report-optimizer 값은 “보고서 개선 프롬프트”나 “수정 로직을 가진 노드 Bean”을 가리키며, 루프가 한 번 돌 때마다 이 옵티마이저가 새로운 버전의 보고서를 생성합니다.
    • approveThreshold (config 안): 평가 점수가 몇 점 이상이면 “승인(approve)”로 간주할지를 결정하는 실수 값입니다. 예시의 0.8은 “평가 점수가 0.8 이상이면 루프를 중단하고 결과를 채택한다”는 의미이며, evaluator가 반환하는 점수 스케일(0~1, 0~100 등)에 맞추어 설계됩니다.

5. 요청 시점의 워크플로 정의 바인딩

선언적 워크플로에서는 실행 엔진(정의 로더, 위상·순서 스케줄, 노드 핸들러 연결)을 한 벌로 두고, 들어오는 요청마다 "이번 실행에 적용할 DSL 문서(YAML)를 어떤 논리 식별자로 불러올지"만 넘기는 패턴이 자연스럽습니다. 식별자는 리소스에 둔 파일·워크플로 id 등과 맞춰 두면, 같은 HTTP 진입점으로 서로 다른 그래프를 골라 태울 수 있어 업무별·테넌트별로 단계 구성이 달라도 엔진 소스에 업무 분기 if를 반복해서 쌓지 않아도 됩니다.

본 과정 실습 화면(Strategic Analysis (YAML))에서도 이 계약을 그대로 씁니다. 질문을 보내기 전에 적용할 YAML 워크플로를 드롭다운 등으로 고르면, 선택한 정의의 논리 식별자가 workflowDefinition 요청 파라미터로 넘어가고, 서버는 chapter8/dagworkflow/{식별자}.yml 같은 경로 규칙에 맞춰 해당 문서만 로드해 실행합니다. API를 직접 호출할 때도 동일한 키로 어떤 정의를 태울지 지정할 수 있어, 화면·클라이언트 모두 "엔진은 고정, 이번만 어떤 YAML인가"만 바꿉니다.

Chapter 9 실습에서도 workflowDefinition으로 정의를 고르는 방식은 같고, 달라지는 점은 chapter9/dagworkflow/ 아래 YAML을 검증층을 거친 뒤 캐시한다는 실행 파이프라인뿐입니다.

왜 이렇게 나누는가

실무에서 자주 바뀌는 것은 노드 나열, 의존 관계, when 분기처럼 "무엇을 돌릴지"이고, 엔진 쪽은 "어떻게 문서를 읽고 의존을 지키며 순서를 잡을지"에 가깝습니다. 식별자로 정의를 선택하면 수정 범위가 문서(YAML)와 호출 계약(어떤 키를 넘길지) 쪽으로 모이고, 엔진은 상대적으로 안정적으로 유지할 수 있어 코드 리뷰·앱 배포 주기와 문서 수정·운영 주기를 나누기 쉽습니다.

기대 효과

  • 정의와 실행의 분리가 서비스 경계(API, 로그)에서도 드러나, "어떤 워크플로 정의를 태웠는지"를 식별자로 감사·추적하기 좋습니다.
  • 엔진 바이너리는 유지한 채 정의만 추가·되돌리기하는 운영 패턴으로 확장하기 쉽습니다.
  • 기본 식별자를 정해 두면 기존 클라이언트는 그대로 두고, 새 흐름만 다른 식별자로 점진적으로 열 수 있습니다.

6. 언제 YAML DSL이 유리한가

“자바를 잘 모르는 사람도 흐름을 보고 말할 수 있게 하고 싶다”, “배포 없이 흐름만 자주 바꾸고 싶다”처럼 느껴질 때 YAML DSL이 특히 잘 맞습니다.

  • 워크플로를 자주 바꿀 때 — 단계 추가·순서 변경·분기 조건 수정을 YAML 파일만 고치면 됩니다. 매번 애플리케이션을 다시 빌드·배포할 부담이 줄어듭니다.
  • 기획자·PO(프로덕트 오너)도 구조를 같이 봐야 할 때 — 긴 자바 코드 대신 노드 목록과 dependsOn이 보이면 “어디서 갈라지는지, 무엇이 끝나야 다음이 도는지”를 대화하기 쉽습니다.
  • 하나의 엔진으로 여러 흐름을 돌릴 때 — 전략 분석·간단 Q&A·다른 리포트처럼 워크플로마다 YAML만 두고 같은 YamlDagWorkflowEngine으로 실행할 수 있습니다.

한 줄로 말하면, “흐름 설계는 YAML(DSL), 공통 실행 규칙은 엔진”으로 나누는 것이고, 그래서 코드는 거의 건드리지 않고 YAML만으로 워크플로를 바꿀 수 있다는 점이 가장 큰 이점입니다.

반대로, 노드 안의 복잡한 알고리즘이나 새로운 종류의 실행 단계를 처음부터 자바로 만들어 넣어야 한다면 그 부분은 여전히 코드 작업이 필요합니다. YAML은 어떤 순서로 어떤 노드를 돌릴지를 정하는 쪽에 강합니다.

7. YAML이 유리한 경우와 실무 적용

"언제 YAML을 쓸지"와 "현장에서는 어떤 형태로 쓰는지"는 같은 축에서 잘 이어집니다. 아래는 선언 표면(YAML)을 두면 이득인 동기와, 그것이 구체화되는 운영 패턴을 한데 묶어 정리한 것입니다. (식별자로 정의를 고르는 흐름은 §5와 맞물립니다.)

  • 비즈니스·기획과 같은 언어로 설계 — PO(프로덕트 오너)·기획과 워크플로를 함께 맞춰야 할 때, 코드보다 읽기 쉬운 YAML이 검토·합의 비용을 줄입니다.
  • 자주 바뀌는 흐름을 배포와 분리 — 노드 나열·의존·when 분기가 앱 배포 주기보다 짧은 주기로 바뀌면, 문서만 고치는 편이 안전합니다.
  • 한 엔진으로 여러 파이프라인 — 전략 분석·리포트 등 종류가 다른 파이프라인을 같은 실행 엔진으로 돌리고, 식별자별 YAML만 추가·교체해 운용합니다.
  • 리포트·분석 파이프라인을 YAML로 나누기 — 예: weekly-report.yml, deep-dive.yml처럼 파일만 나누어 두고, 같은 엔진이 정의 ID만 바꿔 실행합니다. 팀별·제품별로 정의를 분리하기 좋습니다.
  • 고객사·상품별 차이를 문서로만 분기 — 공통 베이스 정의 위에 테넌트별 YAML 오버레이(패치·병합)로 미세 조정하면, 엔진 소스에 업무 분기 if를 반복해서 넣지 않아도 됩니다.

8. 핵심 정리

Chapter 8의 핵심은 “워크플로 정의는 YAML, 실행은 엔진”이라는 역할 분리입니다. Chapter 4~7에서 구축한 SubAgentRegistry, Tool, Task, DAG 엔진 위에 선언적 YAML 레이어를 얹으면, 복잡한 Agent Workflow를 더 안전하고 유연하게 운용할 수 있습니다.

Chapter 9에서는 엔진·DSL 어휘는 그대로 두고, chapter9/dagworkflow/*.yml 로딩 직후 WorkflowDefinitionValidator를 통과한 정의만 캐시해 스케줄링 전에 선언 오류를 걸러 내는 검증층을 더합니다.
