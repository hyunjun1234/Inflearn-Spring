Chapter 9. Validated Agent Workflow DSL

스키마·의존성 검증으로 신뢰하는 YAML 워크플로 DSL

이 장의 전제이자 가장 큰 특징은 실행 엔진은 바꾸지 않는다는 점입니다. YamlDagWorkflowEngine과 Chapter 8과 같은 DSL 어휘(nodes·dependsOn·handler 등)를 쓰고, 워크플로를 늘리는 주된 수단은 역시 DSL 문서(YAML)만 추가·수정하는 것입니다. Chapter 9가 새로 내세우는 것은 다른 엔진이 아니라, chapter9/dagworkflow/*.yml을 읽은 뒤 WorkflowDefinitionValidator를 통과한 정의만 캐시해 스케줄링에 넣기 전에 오타·잘못된 dependsOn·사이클·필수 필드 누락 같은 선언 오류를 걸러 내는 로딩 파이프라인의 검증층입니다.

Chapter 9와 Chapter 8의 차이는 “엔진을 다시 짠다”가 아니라, 위 전제(엔진·DSL 동일, YAML로만 확장)를 유지한 채 로딩 직후 WorkflowDefinitionValidator로 선언 오류를 걸러 주느냐입니다. Chapter 9에서 더해지는 것은 검증층 + chapter9/dagworkflow/ 경로의 검증 로더뿐입니다.

YAML(DSL)은 사람과 팀이 읽고 쓰는 정의 표면이고, DAG는 엔진이 의존성을 해석해 얻는 실행용 방향 비순환 그래프입니다. 로더가 YAML을 WorkflowDefinition으로 옮기고, YamlDagWorkflowEngine이 그 위에서 실행 순서를 정합니다. Chapter 8은 DSL로 정의하는 단계, Chapter 9는 WorkflowDefinitionValidator로 그 정의가 안전한 DAG로 해석되는지 검증하는 단계입니다.

  • 정의(Definition) — Chapter 8과 같은 DSL 스키마(id, nodes, dependsOn, handler …). 필드 요약·주석 예시는 Chapter 8 §3, 도입에 유리한 상황은 Chapter 8 §6에 있습니다.
  • 검증(Validation) — WorkflowDefinitionValidator#validate가 오타·잘못된 dependsOn·사이클·필수 필드 누락 등 구조·DAG 무결성을 확인합니다.
  • 실행(Execution) — 검증을 통과한 정의만 YamlDagWorkflowEngine으로 전달됩니다.

참고: Chapter 9 로더를 확장하면 *.json으로도 같은 DSL(노드·의존성·핸들러)을 정의해 실행할 수 있습니다. 다만 DAG 워크플로 정의는 팀 협업·가독성·주석 작성이 쉬워서 현업에서도 보통 YAML을 더 많이 사용합니다.

1. 개념 정리(검증 추가)

Chapter 7은 DAG를 코드로 직접 구성한 것이고, Chapter 8은 동일한 DAG를 YAML DSL로 정의한 것입니다.

Chapter 9에서는 이 YAML을 classpath:chapter9/dagworkflow/에서 읽은 뒤, WorkflowDefinitionValidator로 구조를 검증하고 통과한 경우에만 실행에 사용합니다.

실행 자체는 Chapter 8과 동일하게 YamlDagWorkflowEngine을 그대로 재사용합니다.

즉, 엔진·DSL 어휘·YAML로만 확장한다는 전제는 Chapter 8과 같고, Chapter 9는 그 위에 로딩 파이프라인의 검증층만 더한 구조입니다.

Chapter 8·9의 흐름은 YAML(DSL) → (Ch9에서 검증) → DAG 해석 → 실행 엔진 → 노드 실행 → 결과로 정리할 수 있습니다.

계층적으로는 다음 세 층으로 나눌 수 있습니다.

  • Definition Loader — YAML을 읽어 WorkflowDefinition으로 변환합니다. Ch9에서는 ValidatedYamlWorkflowDefinitionLoader가 검증 후 캐시합니다.
  • Execution Engine — DAG 의존성을 해석하고 실행 순서를 정합니다(위상 정렬·Kahn 등). YamlDagWorkflowEngine이 담당합니다.
  • Node Handler — SubAgent, Tool, LLM 등 실제 로직을 수행합니다.

Chapter 8 vs 9 — 실행 경로 비교 아래 그림에서 차이는 로딩 단계뿐이고, YamlDagWorkflowEngine 이하(엔진·노드·결과)는 동일합니다.

2. 코드 기반 DAG vs YAML 기반 DAG

코드 기반 DAG(Chapter 7)과 YAML 기반 DAG(Chapter 8·9)를 비교하면 다음과 같습니다.

구분 코드 기반 DAG (Ch7) YAML 기반 DAG (Ch8/9)
정의 방식 Java 코드 YAML DSL
변경 방식 코드 수정 + 배포 YAML 수정
유연성 구조 변경이 무거움 구조 변경이 매우 쉬움
가시성 코드 추적 필요 YAML로 한눈에 파악
검증 컴파일 기반 Ch9에서 Validator로 구조 검증

핵심 차이를 한 줄로 정리하면, DAG는 엔진 내부의 실행 구조이고, YAML은 사람이 워크플로를 적는 DSL(정의 표면)입니다.

Ch7에서는 같은 의존성 그래프를 코드로, Ch8·9에서는 YAML(DSL)로 표현합니다. Ch9는 DSL이 그래프로 옮겨지기 전·직후 무결성을 검증합니다.

3. 실무 적용 시나리오

YAML DSL을 쓰기 좋은 상황·동기는 Chapter 8 §6에서 다룹니다. 이 절은 그다음 단계로, 검증·운영 관점의 적용 예에 가깝습니다.

아래는 “우리 서비스에서도 이렇게 쓸 수 있겠다”고 상상하기 쉬운 예입니다.

  • 리포트·분석 파이프라인을 YAML로 나누기 — 예: weekly-report.yml, deep-dive.yml처럼 파일만 나누어 두고, 같은 엔진이 정의 ID만 바꿔 실행합니다. 팀별·제품별로 정의를 분리하기 좋습니다.
  • 고객사·테넌트마다 흐름이 조금씩 다를 때 — 공통 노드·핸들러는 코드로 두고, 고객사별 YAML만 다르게 두면 커스터마이징 범위가 명확해집니다.
  • A/B 테스트·점진적 롤아웃 — “A안 YAML / B안 YAML”을 두고 요청이나 설정에 따라 어떤 정의를 불러올지 바꿉니다. 코드 배포 없이 실험 구성을 바꾸기 쉽습니다.

운영 환경에서는 Git으로 YAML 변경 이력을 남기고, PR·CI에서 검증(Chapter 9의 Validator와 같은 규칙을 CLI로)까지 묶는 경우가 많습니다.

4. Chapter 8 vs 9 핵심 차이

전제이자 가장 큰 특징은 실행 엔진은 바꾸지 않고 YamlDagWorkflowEngine·Chapter 8과 같은 DSL 어휘를 쓰며, 워크플로 확장은 DSL(YAML) 문서만으로 한다는 점입니다. 그 위에서 Chapter 8은 “설계도(YAML)를 그리는 단계”, Chapter 9는 그 설계도가 실제로 지을 수 있는 형태인지—오타·잘못된 dependsOn·사이클·필수 필드 누락 등—를 스케줄링에 넣기 전에 점검하는 단계에 가깝습니다.

구분 Chapter 8 Chapter 9
역할 DSL 정의 — 워크플로를 YAML로 적는다 DSL 검증 — 적은 내용이 안전한지 본다
상태 일단 실행은 시도할 수 있다 검증을 통과한 것만 안심하고 실행한다
검증 없음 (잘못된 YAML도 로딩·실행 중에야 터질 수 있음) 구조 + DAG 검증 (노드 id, dependsOn, 사이클 등)

정리하면, Chapter 8은 워크플로를 “만드는” 단계이고, Chapter 9는 그 정의를 “믿고 돌려도 되는지 확인하는” 단계입니다. 둘 다 있으면 선언적 설계와 운영 안정성을 같이 가져가기 쉽습니다.

5. 최종 핵심 요약

  • 전제: 실행 엔진은 바꾸지 않는다. YamlDagWorkflowEngine과 Chapter 8과 같은 DSL 어휘로, 워크플로를 늘리는 주된 수단은 DSL 문서(YAML)만 추가·수정하는 것이다.
  • 무엇을 할지는 사람이 읽기 쉬운 YAML(DSL)에 적는다.
  • 언제 어떤 노드를 돌릴지는 DAG 엔진인 YamlDagWorkflowEngine이 의존성을 보고 결정한다.
  • Chapter 9가 더하는 것은 다른 엔진이 아니라, chapter9/dagworkflow/*.yml을 읽은 뒤 WorkflowDefinitionValidator를 통과한 정의만 캐시해 스케줄링 전에 선언 오류를 걸러 내는 로딩 파이프라인의 검증층이다.

즉, 정의(DSL) · 실행(DAG 엔진) · 안전장치(로딩 시 검증) 세 가지를 나누어 생각하면 이 장의 그림이 한 번에 정리됩니다.
