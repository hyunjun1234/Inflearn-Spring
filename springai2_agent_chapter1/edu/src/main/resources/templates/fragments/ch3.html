Chapter 3. Orchestrated Multi-Agent Patterns

Multi-Agent 구조를 실제 서비스 파이프라인으로 구현하기

Chapter 1에서 다룬 Multi-LLM 아키텍처와 Chapter 2의 Agentic Workflow 패턴 위에, 본 장은 이를 단일 오케스트레이션 계층으로 만들어 동작 시킵니다.
Chapter 2에서 설명한 5가지 Pattern을 복합적으로 이용하여 Orchestrated Multi-Agent Pattern을 구체화 합니다.
단계별 상태 전이·예외 격리·재시도까지 포함한 엔드투엔드 흐름을 다루며 목표는 단순 응답 생성이 아니라, 다양한 현장의 운영 환경에서 요구되는 확장성(추가 단계)·품질 안정성(평가·개선)·신뢰성(합의·교차 검증)을 고려한 시스템 설계를 하는 것입니다.

구현하고자 하는 Orchestrated Multi-Agent Pattern은 다음과 같습니다.

  • Strategic Analysis Pattern
    • 전략 품질을 극대화하기 위한 반복 개선 기반 분석 서비스를 구현합니다.
    • 라우팅(Llama: SIMPLE/STRATEGIC)·STRATEGIC일 때만 병렬 분석(GPT/Gemini)·Gemini 평가 + GPT 개선 루프를 오케스트레이션합니다.
    • STARTED → ROUTING → (SIMPLE: LLaMA 단답) 또는 (STRATEGIC: ANALYZING → Parallel → Evaluator-Optimizer ≤4회)
  • Precision Execution Pattern
    • 아이디어를 실제 실행 산출물(코드/문서)로 완성하는 실행 중심 서비스를 구현합니다.
    • LLaMA Refiner(SRS) → GPT Orchestrator(작업 지시 텍스트) → GPT 코드·Gemini 문서 병렬 Worker → join 후 문자열 결합.
    • Refining → Orchestrator → Workers(병렬) → Aggregation → COMPLETED
  • Voting Analysis Pattern
    • 모델 편향 제거 및 신뢰도 향상을 위한 합의 기반 분석 서비스를 구현합니다.
    • 세 모델 병렬(시스템 프롬프트로 관점 분리) → join 수집 → GPT 판정관이 하나를 선택·근거 제시.
    • VOTING_START → Parallel(3) → join → AGGREGATING → GPT Judge → COMPLETED
  • Auto Pattern Routing
    • 질문을 분석해 Strategic / Precision / Voting 중 적합한 파이프라인으로 자동 위임합니다.
    • LLaMA 기반 패턴 분류 → PATTERN_SELECTED → 기존 세 서비스 중 하나 실행
    • Chapter 2 Routing 아이디어를 "완성형 패턴 선택"에 적용한 오케스트레이션 진입점입니다.

2. 다섯 가지 패턴 조합과 Orchestrated Multi-Agent Pattern을 쓰는 이유

Chapter 2에서 다룬 다섯 패턴은 각각 한 가지 역할을 맡는 단위 전략입니다. 실제 업무 파이프라인에서는 보통 여러 패턴을 같이 씁니다.

왜 한 가지 패턴으로는 부족한가

  • Routing — 입력의 업무·질문 유형을 보고 어떤 LLM·어떤 워크플로 경로로 보낼지 미리 정하는 분기가 없으면, 모든 요청을 같은 방식으로만 처리하게 되어 비용·품질·응답 속도를 상황에 맞게 맞추기 어렵습니다.
  • Parallelization — 여러 관점을 동시에 모으지 않으면 분석이 얕아질 수 있습니다.
  • Evaluator-Optimizer — 산출물 품질을 점검하고 고정하지 않으면 개선 루프가 붙지 않습니다.
  • Orchestrator-Workers — 작업을 쪼개 나누지 않으면 대규모 작업·문서화를 안정적으로 처리하기 어렵습니다.
  • Chain — 위 단계들을 정해진 순서로 이어 주는 실행 골격이 됩니다.

Orchestrated Multi-Agent가 필요한 이유

단순히 API를 연달아 호출하는 수준이 아니라, 하나의 서비스 경계에서 실행 순서·상태·로그를 한데 묶어야 운영이 가능합니다. Multi LLM 제품에서는 확장성·재현성·장애 대응을 함께 가져가려면, 패턴 조합을 골라 쓰는 옵션이 아니라 설계의 기본 단위로 보아야 합니다.

Chapter 3에서 다루는 것

본 장에서 다루는 네 가지는 다음과 같습니다.

  • Strategic Analysis — 분석 품질을 높이고 평가·수정을 반복하는 축
  • Precision Execution — 아이디어를 코드·문서 등 실행 산출물로 만드는 축
  • Voting Analysis — 여러 모델의 관점을 모아 신뢰·편향 완화를 다루는 축
  • Auto Pattern Routing — 질문을 보고 세 패턴 중 어느 쪽으로 보낼지 자동으로 고르는 진입·분기

이 네 가지는 같은 Chapter 2 조합이라도 목표(품질·산출물·신뢰)에 따라 가중치를 다르게 둔 완성형 프로파일로 보시면 되고, 자동 라우팅은 그중 하나를 고르는 맨 앞 단계입니다. 다음 절에서 각각의 구조를 구체적으로 정리합니다.

3. Orchestrated Multi-Agent Pattern

아래 세 가지는 용도가 다른 완성형 패턴입니다. Strategic은 품질·반복 개선, Precision은 산출물 생성, Voting은 신뢰도·편향 완화에 초점을 둡니다. 이어지는 Auto Pattern Routing은 질문을 분석해 위 세 패턴 중 하나로 자동 위임하는 오케스트레이션 진입점입니다.

3-1. Strategic Analysis Pattern

전략 품질을 극대화하기 위한 반복 개선 기반 분석 서비스를 구현합니다.

Architecture Flow (StrategicAnalysisService#executeWithMonitoring)

STARTED → ROUTING → (SIMPLE: LLaMA가 단일 프롬프트로 즉시 응답·COMPLETED) 또는 (STRATEGIC: ANALYZING → GPT+Gemini 병렬 → Evaluator-Optimizer 루프 최대 4회 → 최종 보고서)

SIMPLE이면 병렬 분석·평가 루프는 실행되지 않습니다. STRATEGIC일 때만 CompletableFuture 병렬 단계와 Gemini 평가 + GPT 수정 루프가 돌아갑니다.

구조 (코드 기준)

  • LLaMA → SIMPLE / STRATEGIC 라우팅; SIMPLE 경로에서는 동일 LLaMA로 바로 답변
  • GPT → STRATEGIC 시 기술 관점 병렬 분석, 이후 Optimizer(피드백 반영 수정)
  • Gemini → STRATEGIC 시 시장 트렌드 병렬 분석, 이후 Evaluator(80점·PASS 기준 검토)

장점

  • 고급 의사결정 지원
  • 보고서 자동화 최적화

사용 예시

  • ① 기업 인수합병 타당성 분석
  • ② 신규 사업 전략 수립
  • ③ 리스크 기반 의사결정 지원 시스템

3-2. Precision Execution Pattern

아이디어를 실제 실행 산출물(코드/문서)로 완성하는 실행 중심 서비스를 구현합니다.

Architecture Flow (PrecisionExecutionService#executeWithMonitoring)

Refining → Orchestrator → Workers(GPT 코드 + Gemini 문서 병렬) → Aggregation(join + 포맷) → COMPLETED

구조 (코드 기준)

  • LLaMA → SRS Refiner; GPT → Orchestrator(할당 지시 문자열) + Code Worker; Gemini → 한글 가이드 Doc Worker
  • Orchestrator 출력 tasks가 두 Worker의 동일 입력(의존성 DAG·별도 검증 단계 없음)
  • CompletableFuture + 고정 풀(4), safeCall로 단계별 예외 시 오류 문자열 삽입

장점

  • 비용 절감 + 고정밀 처리
  • 전문 도메인 적합

사용 예시

  • ① 금융 보고서 자동 생성 후 규정 맞춤 교정
  • ② 계약서 자동 번역 후 법률 용어 교정
  • ③ 코드 자동 생성 후 최적화 리팩토링

3-3. Voting Analysis Pattern

모델 편향 제거 및 신뢰도 향상을 위한 합의 기반 분석 서비스를 구현합니다.

GPT·Gemini·LLaMA를 동일 user(input)로 병렬 호출(모델별 시스템 프롬프트로 관점 분리)한 뒤, GPT가 판정관으로 최종 선택·사유를 생성합니다.

Architecture Flow (VotingAnalysisService#executeWithMonitoring)

VOTING_START → 병렬 3호출 → join으로 리스트 수집 → AGGREGATING → GPT Judge → COMPLETED

구조 (코드 기준)

  • CompletableFuture.supplyAsync(..., executor) + exceptionally — 호출 실패 시 오류 문자열이 결과 리스트에 포함
  • 별도 점수·다수결 집계 없음; Judge GPT가 3개 텍스트를 보고 "가장 논리적·데이터 풍부" 답을 고르게 유도
  • 반환 문자열에 GPT/Gemini/LLaMA 원문과 ===== 최종 판정 ===== 블록을 함께 포함

장점

  • 편향 감소
  • 신뢰도 향상
  • 고위험 의사결정 적합

사용 예시

  • ① 투자 의사결정 보조 시스템
  • ② 의료 진단 보조 의견 비교
  • ③ 정책 시뮬레이션 결과 교차 분석

3-4. Auto Pattern Routing

사용자 질문을 LLaMA로 STRATEGIC / PRECISION / VOTING 중 하나로 분류한 뒤, 위 세 가지 완성형 파이프라인 중 하나로 자동 위임하는 오케스트레이션 진입점입니다.

Architecture Flow (개념)

Pattern Router (Llama) → PATTERN_SELECTED → 기존 Strategic / Precision / Voting 서비스 executeWithMonitoring 위임

Chapter 2의 Routing 패턴을 "모델 선택"이 아니라 "완성형 패턴 선택"에 적용한 예로 볼 수 있습니다.

사용 예시

  • ① 질문 성격별로 Strategic/Precision/Voting 자동 위임이 필요한 통합 상담 서비스
  • ② 단일 진입점에서 다중 분석 파이프라인을 운영하는 사내 Copilot 게이트웨이
  • ③ 사용자에게 패턴 선택 부담 없이 최적 흐름을 자동 선택하는 업무 지원 시스템

4. Structural Differences Summary (네 패턴 구조 비교)

네 구현은 모두 Multi LLM을 쓰지만 목표 지표가 다릅니다. Strategic은 품질·반복 개선, Precision은 산출물·실행, Voting은 신뢰·합의에 무게를 두고, Auto Pattern Routing은 질문 성격에 맞는 위 세 파이프라인 중 하나를 자동 선택·위임하는 진입 계층입니다.

Pattern Description Main Goal Strength Weakness
Strategic Analysis 질문을 단순/심층으로 나누고, 심층일 때만 여러 모델이 관점을 나눠 분석한 뒤 평가·수정을 반복한다. 보고·전략 품질을 우선한다. 품질 극대화 반복 개선 구조 비용 증가 가능
Precision Execution 모호한 입력을 요구사항 형태로 다듬은 뒤, 코드와 문서(가이드)를 동시에 만들어 하나의 실행 결과물로 묶는다. 만들기·구현에 초점을 둔다. 실행 산출물 생산 확장성 및 역할 분리 구조 복잡도 증가
Voting Analysis 같은 질문을 세 모델이 서로 다른 관점으로 동시에 답하고, 판정관이 한 가지를 고른다. 한 모델만 믿지 않고 교차 검증·신뢰를 높이는 데 맞다. 신뢰도 향상 모델 편향 최소화 다중 호출 비용 증가
Auto Pattern Routing 질문 내용만 보고 Strategic / Precision / Voting 중 하나를 골라 넘긴다. 사용자가 패턴을 고를 필요 없이 진입·분기만 맡는 얇은 관문이다. 올바른 완성형 프로파일로 자동 유도 사용자가 패턴을 고르지 않아도 됨 · 기존 서비스 재사용 분류 오류 시 부적합 파이프라인 실행 가능 · 라우터 단계 지연

Strategic은 품질 중심 설계,
Precision은 생산성 중심 설계,
Voting은 신뢰성 중심 설계,
Auto Pattern Routing은 진입·분기 중심 설계(어떤 완성형 프로파일을 탈지 결정)에 해당합니다.

5. 정리 및 다음 장
