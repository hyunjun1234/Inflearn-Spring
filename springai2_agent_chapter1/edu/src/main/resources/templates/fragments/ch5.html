Chapter 5. Tool-Orchestrated Multi-Agent

Tool을 이용한 실행 레이어 분리 아키텍처

Chapter 4에서는 SubAgentRegistry로 역할(SubAgent) 단위를 나눴습니다. 본 장은 같은 전략 분석 파이프라인을 Tool이라는 실행 단위로 한 번 더 나눕니다.

Main (Main agent, Orchestrator agent)는 단계 정의·순서·재시도 같은 워크플로 제어를 StrategicAnalysisAgentToolOrchestrator에 두고, 각 단계에서 실제로 수행할 작업은 이름 붙은 Tool 구현체에 넘깁니다.

라우팅·경량 응답·기술/시장 병렬 분석·평가·개선 등 흐름을 짜는 일은 오케스트레이터가 맡고, 도메인·I/O(예: RAG, 벡터 스토어, DB·외부 API 조회 등)·LLM 호출 세부는 Tool이 맡습니다. 그래서 오케스트레이션 코드는 언제 무엇을 호출할지에, Tool은 그 호출이 실제로 무엇을 하는지에 집중하는 관심사 분리가 됩니다.

각 Tool은 Spring AI의 @Tool에 맞출 수 있는 단일 책임 실행 단위로 두고, ToolRegistry에 키로 등록합니다. 오케스트레이터는 toolRegistry.require(…)로 단계에 맞는 Tool만 고릅니다. Tool 안쪽에서는 Chapter 4처럼 SubAgent를 경유해 Llama·GPT·Gemini 등 역할별 ChatClient를 고를 수 있어, 워크플로 경계 = Tool, 모델·프롬프트 경계 = SubAgent로 겹쳐 씁니다. Chapter 1~3의 Multi-LLM 전략을 유지하면서도 모듈을 테스트·교체하기 쉽습니다.

RAG·벡터 스토어·DB 조회처럼 외부 근거를 끌어오는 부작용(side effect)이 큰 작업도 Tool로 묶어 두면, 오케스트레이터는 필요할 때만 그 Tool을 불러 최신·사실 기반 컨텍스트를 얹을 수 있습니다. 이어지는 Chapter 6 이후 Task·외부 연동 실습으로 확장하는 발판이 됩니다.

한 줄 요약 — Chapter 4의 SubAgent 위에 Tool 경계를 더해, 실행 레이어를 한 층 더 나눈 장입니다.

2. @Tool vs StrategicTool + ToolRegistry

Spring AI @Tool이 쓰이는 전형적인 경우

채팅 모델이 함수·도구 목록을 보고, 대화 맥락에 따라 언제 어떤 도구를 호출할지 스스로 결정할 때입니다. Spring AI는 그 과정을 프롬프트·스키마·콜백으로 묶어 주는 패턴을 제공합니다.

이 코드베이스의 Chapter 5

StrategicAnalysisAgentToolOrchestrator가 toolRegistry.require("routing") → … 처럼 고정된 워크플로로 단계를 호출합니다. 즉 호출 주체는 LLM이 아니라 Java 코드이고, 도구는 “모델에게 노출되는 함수”가 아니라 이름으로 꺼내 쓰는 실행 단위에 가깝습니다.

3. Agent-only vs Agent + Tool 차이점 정리

Agent-only vs Agent + Tool을 장단점 기준으로 한 번에 비교해 보면 아래와 같습니다. 특히 RAG(검색 증강 생성)나 데이터베이스 연동은 “모델이 기억에만 의존하지 않고, 실제 문서·DB에서 근거를 가져오게” 하려면 결국 Tool(또는 그에 준하는 실행 단위)로 분리해 두고 호출하는 경우가 많습니다.

관점 Agent-only
(LLM 위주)		 Agent + Tool
(앱 코드가 단계 조립)
근거 학습 때 본 내용 위주로 답한다 → 없는 정보를 지어낼 수 있다(환각) 검색(RAG)·DB·API로 가져온 결과를 넣고 답하게 할 수 있다
재현 매번 조금씩 달라질 수 있다 Tool 호출 방식을 고정하면 비슷하게 맞추기 쉽고, 로그로 추적하기도 좋다
시스템 메시지
(역할별 지시문)		 한 프롬프트에 역할 지시가 섞이기 쉽고, 재사용은 복붙·중복으로 이어진다. 수정 시 어느 단계 문장인지 찾기도 어렵다 systemMessage()로 역할별 지시를 한곳에 두면 오케스트레이터는 입력만 넘기면 되고, 문구만 바꿔도 해당 단계 전체에 반영되며 같은 Tool로 재사용하기 쉽다
난이도 처음 만들기는 가볍고, 시연·POC(개념 증명)에 잘 맞는다 처음엔 클래스·연결이 많아진다 → 대신 실서비스에서 필요한 모니터링·장애 대응에 유리하다

이 장의 Agent + Tool 예제에서는 각 StrategicTool이 systemMessage()로 단계별 페르소나·출력 규칙을 담당합니다. 라우팅·기술 분석·평가처럼 서로 다른 지시가 필요할 때, 파일(도구) 단위로 나눠 두면 수정 범위가 명확하고 동일 Tool을 레지스트리·오케스트레이터 여러 곳에서 호출해도 지시문이 한결같이 유지됩니다.

4. 언제 Agent만 쓰면 좋은가

5. 언제 Tool이 필요한가

이 경우는 100% Tool 구조가 필요합니다.

  • API 연동
  • 자동 업무 처리
