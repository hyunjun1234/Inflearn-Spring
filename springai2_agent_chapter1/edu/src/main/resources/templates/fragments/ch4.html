Chapter 4. Multi-Agent Architecture

SubAgent 분리 전략과 Agent Registry 내부 구조

Agent 개념 요약

Agent 한 줄 정의 — “스스로 판단하고 행동하는 AI 단위”

조금 더 정확한 정의 — “목표를 가지고, 계획하고, 도구를 사용해 결과를 만들어내는 실행 주체”

LLM과 Agent의 차이

기존 LLM
입력 → 응답. 단순 질문·응답에 가깝다.
Agent
Goal(무엇을 할지) → Reasoning(어떻게 할지) → Action(실행) → Tool(외부 API·DB·검색)이 끊기지 않은 한 줄의 흐름으로 순서대로 이어지고, Action·Tool에서 나온 관측(observation)을 그다음 Reasoning의 입력으로 넣어 같은 순서의 처리를 이어 갈 수 있다.

Agent 내부 구조 (핵심 네 가지)

  • Goal (목표) — 무엇을 해야 하는가
  • Reasoning (판단) — 어떻게 할지 결정
  • Action (행동) — 실제 실행
  • Tool (도구) — 외부 API, DB, 검색 등

Agent와 단순 코드의 차이

일반 코드 (weatherApi.call(); 등)
호출 순서와 분기가 코드에 고정된다.
Agent
상황을 판단한 뒤 필요한 Tool을 고르고 실행한다. 행동이 유연하다.

예시 (직관적)

사용자 요청 — “서울 날씨 알려줘”

Agent 동작

  1. 질문 분석
  2. 날씨 API 선택
  3. API 호출
  4. 결과 정리
  5. 응답 생성

Agent의 핵심 특징

  • 자율성 (Autonomy) — 스스로 다음 행동을 결정한다.
  • Tool 사용 — 외부 시스템과 연결한다.
  • 반복 실행 — 실패나 부족한 결과에 맞춰 다시 시도할 수 있다.
  • 상태 기반 — Memory 등 누적 맥락을 활용한다.

Agent 종류

  • 단일 Agent — 하나의 주체가 전체 작업을 수행한다.
  • Multi-Agent (다중 에이전트) — Planner, Executor, Refiner, Validator 등으로 역할을 나눈다. 본 장의 Main·Sub 구조도 이 계열에 해당한다.

Agentic Workflow와의 관계

본 과정에서 Agentic Workflow(Chapter 2)는 “한 번의 프롬프트 응답”이 아니라 상태·분기·병렬·재시도·관측까지 포함한 엔드투엔드 실행 흐름을 뜻합니다. 그 흐름 안에서 어느 단계를 언제·어떤 조건으로 이어 갈지를 정리하는 제어를 오케스트레이션(Orchestration)이라고 보면, Agent 내부의 판단과는 별도로 호출 순서·분기·병렬을 코드나 엔진이 맡는 층입니다.

단일 Agent는 그 흐름을 한 실행 주체가 Goal→Reasoning→Action→Tool로 밀고 가는 형태에 가깝고, Multi-Agent는 같은 목표를 역할이 다른 Agent(본 장의 Main·Sub, 이후 장의 노드·Tool 담당 주체 등)로 나누어 맡기는 형태입니다. Multi-Agent일수록 오케스트레이션은 누구를 언제 부를지를 잡는 바깥 조율층(본 장의 Main 오케스트레이터, 이후 DagWorkflowEngine·YAML 엔진 등)으로 더 분명해집니다.

이 흐름을 본 과정 축으로 보면, Chapter 2·3을 단일 Agent 관점으로 이해할 수 있고, 이후 장은 같은 문제를 Multi-Agent 관점으로 확장해 가는 구성입니다. Chapter 4~6은 주로 코드·런타임이 오케스트레이션을 맡아 단계 순서와 Tool 호출을 잡고, Chapter 7~9는 DAG·YAML DSL로 그 워크플로를 그래프·선언적으로 옮겨 같은 전략 분석 시나리오를 확장합니다. 정리하면 Agentic Workflow는 Agent가 일을 나눠 실행하고(누가 할지), Orchestration이 그 실행 순서를 조율해(언제·어떻게 이어갈지), 사용자 요청 하나가 최종 응답으로 끝날 때까지 전 과정을 연결해 주는 실행 흐름입니다.

한 줄로 정리

  • Agent — 목표를 기준으로 판단·실행하며 결과를 만들어 내는 실행 주체
  • Multi-Agent — 하나의 목표를 역할별 Agent로 분담해 협업하는 구조
  • Orchestration — 각 Agent/Tool을 언제 어떤 순서·조건으로 호출할지 조율하는 제어층
  • Agentic Workflow — 역할 분담과 실행 순서 조율을 묶어, 요청부터 최종 응답까지 연결한 전체 흐름

가장 중요한 차이

LLM은 “말하는 AI”에 가깝고, Agent는 “일하는 AI”에 가깝다.

Chapter 1~3에서는 여러 LLM을 쓰는 법과 한 서비스 안에서 파이프라인을 도는 법을 배웠습니다. Chapter 3의 StrategicAnalysisService는 한 클래스가 Llama·GPT·Gemini를 직접 호출하는 구조였습니다.

본 장은 그 한계를 넘어, Main (Main agent, Orchestrator agent)이 맡는 제어 계층과 Sub (Sub agent, Tool agent 등)가 맡는 역할 전용 실행 계층 (SubAgent)를 나눈 Multi-Agent 구조를 다룹니다.

전략 분석 파이프라인(라우팅·간단 응답·기술·시장 병렬 분석·평가·개선 루프 등)에서 단계를 정하고, 분기·병렬·반복을 짜는 일은 Main 쪽 StrategicAnalysisAgentOrchestrator가 맡습니다. 각 단계의 LLM 호출과 세부 프롬프트는 역할마다 쪼갠 SubAgent에 넘깁니다.

그 결과 오케스트레이션 코드는 “무엇을 언제 실행할지”에 집중하고, Sub 쪽은 “한 역할의 입·출력 계약”만 지키면 됩니다.

Sub는 SubAgent를 구현한 작고 단일 책임의 Spring 빈으로 두고, 기동 시 SubAgentRegistry가 name()으로 모읍니다. Main은 require("routing")처럼 이름만으로 조회해 execute만 호출하면 되고, 역할마다 @Qualifier로 다른 ChatClient를 주입하면 Chapter 1의 Multi-LLM 전략을 에이전트 단계마다 그대로 이어 쓸 수 있습니다.

1. Main Agent와 Sub Agent 구조


🔹 Main(Main agent, Orchestrator agent) (메인 오케스트레이터)

Main(Main agent, Orchestrator agent)는 단일 LLM 호출로 모든 작업을 처리하는 구조가 아니라, Java 기반 오케스트레이션 계층에서 단계·분기·병렬·반복 흐름을 제어합니다. Ch4Controller는 POST /ch4/strategic-analysis 요청 시 클라이언트가 SSE 구독과 맞추기 위해 넘긴 workflowId(UUID)와 prompt를 받아 StrategicAnalysisAgentService#executeWithMonitoring()에 전달합니다. 실제 라우팅·병렬 분석·평가·개선 루프의 실행 순서는 StrategicAnalysisAgentOrchestrator가 담당합니다. 단계별 진행은 Redis의 WorkflowStatusPublisher로 전송되며, 실습 화면은 동일 workflowId로 SSE(Server-Sent Events)를 구독해 상태를 확인합니다.

🔹 Sub(Sub agent, Tool agent 등) (서브 에이전트)

Sub(Sub agent, Tool agent 등)는 SubAgent 인터페이스(name(), description(), execute(String))를 구현한 작은 단위의 Spring 컴포넌트이며, 하나의 역할만 수행하도록 설계됩니다. 입력은 단일 문자열이고 출력도 한 번의 LLM 호출로 문자열을 반환하는 구조이기 때문에, 라우팅·요약·기술 분석·시장 분석·보고서 평가처럼 “한 단계에서 하나의 작업만 수행하는” 역할에 매우 적합합니다. Main(Main agent, Orchestrator agent)는 subAgentRegistry.require("routing")처럼 이름으로 서브 에이전트를 조회한 뒤 execute()만 호출하여 각 단계를 순차적으로 실행합니다.

과정에서는 날씨·외부 API처럼 Tool·함수 호출이 중심인 Sub를 Tool agent로 짚어 설명합니다. Sub(Sub agent, Tool agent 등)의 등에는 라우팅·요약처럼 LLM 호출만으로 역할을 나눈 Sub도 포함됩니다.

🔹 SubAgentRegistry (서브 에이전트 관리 구조)

SubAgentRegistry는 Spring이 자동으로 주입한 모든 Sub(Sub agent, Tool agent 등) 빈을 name() 기준으로 Map 형태로 수집하고 관리하는 역할을 합니다. 동일한 이름의 Sub(Sub agent, Tool agent 등)가 두 개 이상 존재하면 애플리케이션 기동 시 즉시 예외가 발생하므로, 오케스트레이션에서 쓰는 키(예: StrategicAgentKeys.ROUTING, 실제 문자열 "routing")와 각 SubAgent 구현의 name()이 정확히 일치하도록 맞춥니다. 이 구조 덕분에 Main(Main agent, Orchestrator agent)는 특정 구현 클래스에 의존하지 않고, 이름 기반으로 유연하게 서브 에이전트를 교체하거나 확장할 수 있습니다.

✔ Chapter 7 DAG 엔진에서도 동일 레지스트리를 재사용합니다.

1-2. Agent와 SubAgent 역할 분리

① Main(Main agent, Orchestrator agent) (메인 오케스트레이터)

역할은 단 하나입니다.

“어떤 SubAgent를 언제 실행할 것인지 결정”

즉

  • 단계 제어
  • 실행 순서 제어
  • 병렬 실행 제어
  • 반복 실행 제어

구조적으로 보면

AI가 직접 일하는 구조 → AI를 관리하는 구조

② SubAgent (실제 일을 하는 AI)

SubAgent는 하나의 역할만 수행합니다.

예시

  • 라우팅 전용 SubAgent
  • 기술 분석 전용 SubAgent
  • 시장 분석 전용 SubAgent
  • 평가 전용 SubAgent
  • 간단 질문 전용 SubAgent

즉 하나의 SubAgent = 하나의 역할

1-4. 실행 흐름 구조

STRATEGIC 요청이 들어오면 실행 흐름은 이렇게 됩니다.

  1. Step 1. Routing SubAgent 실행
  2. Step 2. (STRATEGIC인 경우) 기술 분석 SubAgent 실행 · 시장 분석 SubAgent 실행
  3. Step 3. 결과 병합
  4. Step 4. 평가 SubAgent 실행
  5. Step 5. 필요하면 다시 수정 후 반복

즉 Routing → Analysis → Merge → Evaluate → Optimize

1-5. 가장 중요한 설계 포인트

이 구조의 핵심은 이것입니다.

Main(Main agent, Orchestrator agent)는 “누가 실행될지”만 알고
SubAgent는 “무엇을 실행할지”만 알고 있습니다.

즉

역할 책임
Main(Main agent, Orchestrator agent) 실행 순서 제어
Sub(Sub agent, Tool agent 등) · SubAgent 실제 LLM 작업 수행
Registry SubAgent 관리

1-6. 왜 SubAgent 구조를 사용하는가

기존 구조는 이런 문제를 가지고 있습니다.

  • 하나의 Service 안에서 Llama 호출, GPT 호출, Gemini 호출
  • 프롬프트 10개 이상

결과

  • 코드가 계속 커짐
  • 유지보수 어려움
  • 기능 추가 어려움

하지만 SubAgent 구조는 이렇게 바뀝니다.

기능 추가 = SubAgent 하나 추가

즉 확장 가능한 Agent 구조

1-7. Chapter 4 구조 핵심 요약

이 장의 핵심은 아래 한 줄입니다.

하나의 큰 Agent → 여러 개의 역할 기반 SubAgent 구조

그리고 구조는 이렇게 정리됩니다.

  • Main(Main agent, Orchestrator agent) = 오케스트레이터
  • Sub(Sub agent, Tool agent 등) · SubAgent = 역할 전용 AI
  • Registry = SubAgent 관리 시스템

4. 실행 파이프라인 (STRATEGIC 경로 요약)


  1. ROUTING — routing 서브 에이전트가 분류
  2. SIMPLE — simple-query만 호출 후 종료
  3. ANALYZING — technical-analysis와 market-analysis를 CompletableFuture로 병렬 실행 후, 결과를 하나의 초안 문자열로 병합
  4. EVALUATING / OPTIMIZING — 최대 4회: report-evaluator로 평가 → PASS면 완료, 아니면 ReportOptimizerSubagent#optimize로 초안 갱신 후 반복

각 단계는 WorkflowStatusPublisher로 Redis에 발행되며, 브라우저는 동일 workflowId로 SSE 스트림을 구독해 진행 상황을 표시합니다.

🔹 바뀐 점 (Chapter 4 설계 의도)

  • 역할 분리 — Chapter 3은 한 서비스 클래스 안에서 llamaClient, gptClient, geminiClient를 직접 호출합니다. Chapter 4는 각 역할을 SubAgent (또는 Optimizer 전용 빈)로 나누고, 오케스트레이터는 “누구를 부를지”만 결정합니다.
  • 확장·재사용 — 새 단계를 추가할 때 서비스 본문을 비대하게 늘리기보다, SubAgent 구현 클래스를 추가하고 레지스트리에 자동 등록되는 방식으로 맞춥니다. (Chapter 7 DAG 노드에서 같은 SubAgentRegistry를 쓰는 이유와 연결됩니다.)
  • 계약의 명시 — SubAgent는 “단일 문자열 in / 문자열 out”으로 통일됩니다. Optimizer처럼 의미상 입력이 두 개이면, ReportOptimizerSubagent가 합친 한 문자열을 받아 내부에서 나눕니다.
  • 엔드포인트 — Chapter 3은 컨트롤러 경로가 /ch3/... 계열이고, Chapter 4 실습은 /ch4/strategic-analysis와 StrategicAnalysisAgentService를 사용합니다.

Chapter 5에서는 같은 비즈니스를 도구 빈으로 쪼갠 뒤 StrategicAnalysisOrchestrator가 Chapter 4와 같은 순서로 Java 코드 워크플로를 실행하는 형태로 이어지고, Chapter 6에서는 커뮤니티 Task tool과 Markdown 서브에이전트 실습이 이어집니다. 본 Chapter 4 문서는 순수 Java 오케스트레이션 + SubAgent 레지스트리 패턴에 맞춰 정리되었습니다.
