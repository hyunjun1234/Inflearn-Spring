Chapter 2. Agentic Workflow Patterns

실무에서 사용하는 5가지 Agent Workflow 패턴

Chapter 1에서 정리한 Multi-LLM 아키텍처 위에, 본 장은 LLM 호출을 상태·분기·동시성·피드백 루프가 있는 오케스트레이션으로 묶는 패턴을 다룹니다.
즉 “한 번의 프롬프트 응답”이 아니라, 요청을 단계화하고 모델을 역할별로 나누며, 필요 시 평가·재시도까지 포함하는 엔터프라이즈형 워크플로 관점입니다.

참고 프레임워크로, Spring AI 문서의 Effective Agents가 제시하는 워크플로 유형과 Anthropic 엔지니어링 글 Building Effective Agents가 강조하는 단순한 추상화·명시적 구성(composability)을 기반으로 5가지의 Patter으로 나누어서 설명 합니다.
이후 과정에서 공부 할 Multi Agent 구조를 만들기 위한 검증 가능한 단위 패턴을 공부 하도록 하겠습니다.

구현하고자 하는 Orchestrated Multi-Agent Pattern은 다음과 같습니다.

  • 1) Chain Workflow
    • 작업을 순차적으로 연결하여 이전 단계의 결과를 다음 단계의 입력으로 전달하는 구조
    • 사용 이유: 단계적 사고 및 절차적 실행 보장
  • 2) Parallelization Workflow
    • 동일 입력을 여러 LLM에 병렬로 실행하고 결과를 병합하는 구조
    • 사용 이유: 모델 간 전문성 동시 활용
  • 3) Routing Workflow
    • 입력 조건에 따라 최적의 LLM으로 분기 처리하는 구조
    • 사용 이유: 요청 난이도·유형별 최적 모델 선택
  • 4) Orchestrator-Workers
    • 중앙 Orchestrator가 Multi LLM을 각 역할 별 실행 후 최종결합 하는 구조
    • 사용 이유: 역할 기반 책임 분리 구조 구현
  • 5) Evaluator-Optimizer
    • 생성 결과를 평가하고 개선하는 반복 구조
    • 사용 이유: 반복 개선을 통한 품질 안정화

1. Agentic Workflow와 Multi LLM 전략

본 시스템은 GPT, Gemini, Llama 세 LLM을 전략적으로 활용해 Agentic Workflow를 구성합니다. LLM을 “도구 한 개”가 아니라 협업하는 단계·역할로 나누어 쓰는 것이 핵심입니다.

Agentic Workflow는 단순한 LLM 호출이 아니라, 판단(Reasoning) + 모델 선택(Model Selection) + 실행(Execution) + 평가(Evaluation) 을 포함하는 의사결정 흐름입니다. 아래는 이 장에서 반복해서 등장하는 추상 흐름입니다.

의사결정 루프 (개념)

입력

사용자 요청 · 컨텍스트

↓
Reasoning

의도·난이도·제약 파악

↓
Model selection

GPT / Gemini / Llama 선택

라우팅·비용·보안 정책 반영

↓
Execution

Chain · Parallel · Orchestrator 등

패턴별 워크플로 실행

↓
Evaluation

품질 검증 · 필요 시 재시도

↓
출력

통합 응답 · 로그

이후 장(Chapter 3~4)에서는 이 루프를 서비스·서브에이전트로 구체화합니다.

서로 다른 LLM을 쓰는 이유는 한 모델에 모든 부담을 주지 않고, 단계별로 강점을 나누기 위함입니다.

  • GPT — 복잡한 추론, 코드 생성, 고품질 텍스트에 강점
  • Gemini — 응답 속도, 멀티모달·대규모 컨텍스트 활용에 유리한 경우가 많음
  • Llama — 로컬 실행, 민감 데이터 처리, 비용 통제에 유리

단일 모델에 의존하지 않고, 품질 + 비용 + 성능 + 보안을 종합적으로 고려하여 각 Workflow 단계에서 최적의 모델을 선택합니다.

2. Python LangChain과의 비교

구분 Spring AI (Multi-LLM Architecture) LangChain (Python Ecosystem)
통합·실행 환경 Java/Kotlin·Spring Boot와 한데 묶어 Security·데이터·메시징 등 기업 스택까지 운영 관점에서 일관되게 가져가기 쉽다. Python·노트북·데이터 스택과 맞물려 에이전트·툴·체인을 빠르게 엮고 검증하기 좋다.
멀티 LLM·워크플로 여러 LLM과 분기·병렬·라우팅을 서비스 코드로 구조화하기 유리하다. 모델·체인 교체는 쉬우나, 멀티 LLM 전략과 복잡한 흐름은 직접 설계한다.
스트리밍·실시간 응답 WebFlux·SSE 등으로 토큰 스트림을 HTTP API에 실어 보내기 쉽고, 게이트웨이·타임아웃·연결 유지와 맞춘 운영 패턴을 잡기 좋다. 스트리밍 API·콜백은 풍부하나, 실서비스에서는 프록시·타임아웃·버퍼링·배포 형태를 애플리케이션과 인프라 쪽에서 따로 설계하는 경우가 많다.
적합한 활용 기존 시스템·레거시와 다종 연동(사내·외부 HTTP API, DB, 메시징·이벤트, 배치 등)을 동일 애플리케이션 경계(Spring Security·트랜잭션·관측) 안에서 묶어 운영·감사·SLA를 맞춰야 하는 장기 운영형 서비스에 유리하다. 현장에서 익숙한 Python·노트북으로 에이전트·툴·체인을 빠르게 붙여 보고, 프롬프트·모델·외부 API가 요구에 맞는지 PoC·시연·요구 맞춤으로 확인할 때 쓰기 좋다. 반면 사내 여러 시스템과 계정·권한·로그·배포까지 묶어 상시 서비스로 가져가려면, 보통 앱·인프라·운영 규칙을 따로 잡는 단계가 필요하다.

현장에서는 (제품·플랫폼)

앞 표의 Spring AI·LangChain은 애플리케이션 코드로 오케스트레이션을 짜는 예에 가깝습니다.

제품·플랫폼으로 묶는 경우

화면·정책만으로 호출 순서와 연동을 이어 오케스트레이션을 만들 수도 있으며, 현장에서도 자주 씁니다.

  • n8n — HTTP·웹훅·DB·SaaS·LLM API 등을 노드로 이어 자동화
  • Dify — 프롬프트·RAG·에이전트를 묶는 LLM 앱 플랫폼
  • Bedrock·Azure OpenAI·Vertex AI 등 — 클라우드 상용 API·관리형 API
  • 내부 게이트 — 사내 관리형 API·정책 진입점

다만 업무 규칙·감사·다중 환경·기존 시스템 연동이 깊어지면 제품만으로는 한계가 드러납니다. 제품으로 충분한 경우와 반드시 코드로 직접 구현해야 하는 경우를 가려 보는 것이 중요합니다.

직접 코드가 특히 필요할 때

Spring AI·LangChain처럼 흐름을 코드로 짜는 쪽이 두드러지는 때는 아래에 가깝습니다.

  • PoC(개념 검증) 이후 실서비스 운영에 들어갔는데, 제품·로우코드(n8n·Dify 등) 화면만으로는 업무 규칙·예외 처리·재시도·한 묶음의 작업 범위를 의도한 대로 정확히 표현하기 어려울 때
  • 감사·장애·비용처럼 누가 무엇을 호출했는지 따라가야 할 때
  • 사내에 맞춰 둔 API·이벤트 약속이 빌더의 고정 카드 조합으로는 닿지 않을 때

코드로 두면 좋은 이유

  • 처리 순서가 저장소(Git 등)·코드 리뷰·테스트 기록에 남아, 같은 조건에 재현·설명하기 쉽다
  • 화면 설정만으로는 숨은 조건·예외·데이터 흐름이 잘 드러나지 않고, 운영 중 모델·프롬프트·툴을 바꿀 때 무엇에 영향이 가는지 정리하기 어렵다
  • 레거시·DB·메시지·권한 등 기존 시스템과 연동하거나, 이미 돌아가는 서비스에 AI를 끼울 때는 연동 지점·호출 순서·권한 경계를 코드로 밝혀 두어야 유지·감사에 대응하기 쉽다

본 과정의 워크플로·Tool·Task·DAG는 이런 제품 위에 얹거나, 제품만으로 부족한 실행 뼈대를 만드는 데 바로 이어집니다.

본 과정의 초점

이런 제품 선택과 별도로, 요구가 코드 레벨까지 내려왔을 때 흐름을 설계·구현할 수 있는 역량을 다룹니다.

다섯 가지 패턴을 먼저 공부하는 이유는, 이후에 나오는 오케스트레이션·멀티 LLM 설계가 결국 순차(Chain)·병렬·분기(Routing)·품질 루프(Evaluator–Optimizer)·역할 분담(Orchestrator–Workers) 같은 조합으로 표현되기 때문입니다. Spring AI 문서와 현장에서도 이 이름으로 대화가 통하므로, 공통 어휘를 갖추면 요구를 구조로 옮기고 코드·리뷰·문서에서 같은 그림을 가리키기 쉽습니다. 임의로 짠 if/호출 나열만으로는 “어떤 흐름인지”가 팀과 문서에 남기 어렵고, 나중에 Tool·DAG·YAML로 키울 때도 뼈대를 설명할 말이 부족해집니다.

우선 아래 §3에서 다섯 가지 Agentic Workflow 패턴(Chain, Parallelization, Routing, Evaluator–Optimizer, Orchestrator–Workers)을 실습하며 익힙니다. 이어서 이 패턴들을 조합·확장하는 시각으로 넘어가, Chapter 4~9에서는 멀티 에이전트·Tool·Task/에이전트 런타임·DAG 오케스트레이션·YAML 선언적 워크플로·로딩 검증까지 실제 서비스에 가까운 오케스트레이션을 차례로 다룹니다.

정리하면 기본 패턴 → 패턴 조합·확장 → Chapter 4~9 심화 순으로 이어지도록 구성되어 있습니다.

3. 5가지 Agentic Workflow 패턴 (Multi LLM 적용)

아래 다섯 패턴은 Spring AI 문서의 Effective Agents 섹션과 대응합니다. 본 프로젝트의 Ch2Controller(/ch2/...)는 각 패턴별로 HTTP POST API를 제공하며, 왼쪽 메뉴 실습 화면에서 호출해 볼 수 있습니다.

3-1. Chain Workflow

작업을 순차적으로 연결하여 이전 단계의 결과를 다음 단계의 입력으로 전달하는 구조입니다.

구조 (실습 코드 ChainWorkflowService와 동일)

  • Step 1 → Llama: 핵심 키워드 추출
  • Step 2 → GPT: 키워드 기반 홍보 문구 작성
  • Step 3 → Gemini: 톤 다듬기 및 영어 번역 포함 검수

특징

  • 순차적 Pipeline 처리
  • 단계별 책임 분리

장점

  • 복잡한 문제를 단계별로 분해 가능
  • 각 단계의 품질을 개별적으로 개선 가능
  • 테스트 및 유지보수 용이

사용 예시

  • ① 계약서 분석 → 핵심 조항 추출 → 리스크 요약 보고서 생성
  • ② 기술 문서 분석 → 비전문가용 설명 생성 → 블로그 콘텐츠 작성
  • ③ 고객 VOC 분석 → 감정 분석 → 개선 전략 도출

3-2. Parallelization Workflow

동일 입력을 여러 LLM에 병렬로 실행하고 결과를 병합하는 구조입니다.

구조

  • 동일 요청을 GPT / Gemini / Llama에 동시에 전달
  • Aggregator가 결과 병합

특징

  • 병렬 실행 구조
  • 다양한 시각 확보

장점

  • 응답 속도(벽시계 시간) 절약 가능
  • 교차 검증 가능
  • 신뢰도 상승

사용 예시

  • ① 투자 리포트 분석 후 3개 모델 의견 비교
  • ② 정책 문서 요약 정확도 비교 후 최적 결과 선택
  • ③ 마케팅 카피 3가지 버전 생성 후 A/B 테스트

3-3. Routing Workflow

입력 조건에 따라 최적의 LLM으로 분기 처리하는 구조입니다.

구조

  • Request Analyzer → 모델 선택 → 실행

특징

  • 요청 유형 기반 동적 모델 선택
  • 전략적 비용 관리

장점

  • 벤더 종속성 최소화
  • 성능/비용 균형 최적화

사용 예시

  • ① 코드 생성 요청 → GPT
  • ② 이미지 포함 설명 요청 → Gemini
  • ③ 내부 보안 데이터 질의 → Llama (로컬)

3-4. Orchestrator-Workers

중앙 Orchestrator가 GPT, Gemini, Llama를 Worker로 제어하는 구조입니다.

구조

  • GPT가 작업을 세부 Task로 분해
  • Gemini/Llama가 세부 작업 수행
  • 결과 통합 후 최종 보고서 생성

특징

  • 대규모 작업 분산 처리
  • 확장성 높은 구조

장점

  • 대용량 문서 처리 가능
  • 병렬 확장 구조
  • 엔터프라이즈 적합

사용 예시

  • ① 200페이지 보고서 → 챕터별 요약 → 전체 Executive Summary 생성
  • ② 시장 조사 데이터 → 산업별 분석 → 전략 도출
  • ③ 고객 데이터 세분화 → 그룹별 인사이트 분석

3-5. Evaluator-Optimizer

생성 결과를 평가하고 개선하는 반복 구조입니다. Chapter 3·4의 전략 분석 파이프라인에서도 평가·개선 루프가 이 패턴에 해당합니다.

구조

  • Generator(GPT) → Evaluator(Gemini) → 개선 반복

특징

  • Self-Refinement Loop
  • 품질 중심 설계

장점

  • 정확도 향상
  • 오류 감소
  • 고품질 콘텐츠 확보

사용 예시

  • ① 법률 문서 초안 생성 → 규정 준수 여부 평가 → 수정 반복
  • ② 의료 보고서 작성 → 의학적 오류 검증 → 개선
  • ③ 기술 설계서 자동 생성 → 품질 점검 → 리팩토링

4. 5가지 패턴 비교

난이도·속도·확장성은 도메인과 구현에 따라 달라지므로, 아래 표는 강의용 상대 비교로만 쓰면 됩니다. Chain은 이해하기 쉽지만 단계가 길어질수록 지연은 커지고, Evaluator는 품질은 좋아도 반복 비용이 듭니다.

패턴 Multi LLM 활용도 속도 확장성 난이도
Chain 단계별 분리 활용 느림 중간 쉬움
Parallel 동시 실행 빠름 높음 보통
Routing 조건 기반 선택 빠름 높음 보통
Orchestrator 협업 구조 보통 매우 높음 어려움
Evaluator 역할 분리 기반 반복 느림(반복) 높음 어려움

5. 정리 및 다음 장

Multi LLM 기반 Agentic Workflow는 단일 모델의 한계를 넘어 품질, 비용, 성능, 보안을 동시에 고려하는 설계 패턴입니다. 이 장의 다섯 패턴은 이후 Chapter 3에서 하나의 오케스트레이션 서비스로 엮이고, Chapter 4에서는 SubAgent·레지스트리로 역할을 더 잘게 나누는 방향으로 확장됩니다.
